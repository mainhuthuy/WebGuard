# Task 4.4 — CI: Backend Pipeline (GitHub Actions: Ruff + Pytest)

> **Mục tiêu:** Mỗi khi có PR đụng vào backend, GitHub tự động chạy **lint (Ruff)** và **test (Pytest)**. Code lỗi style/bug sẽ bị chặn *trước khi* merge, không phụ thuộc việc dev có nhớ chạy tay hay không.
>
> File triển khai: `.github/workflows/backend-ci.yml`

---

## 📚 Lý thuyết

### CI là gì?
**Continuous Integration** = mỗi lần gộp code, một máy chủ sạch tự build + kiểm tra. Giá trị cốt lõi: **"chạy được trên máy tôi" không còn là bằng chứng** — kết quả duy nhất được tin là kết quả trên môi trường sạch, lặp lại được.

### Các khái niệm GitHub Actions
| Khái niệm | Ý nghĩa |
|---|---|
| **Workflow** | 1 file YAML trong `.github/workflows/` |
| **Trigger (`on`)** | Sự kiện kích hoạt: `pull_request`, `push`, `schedule`... |
| **Job** | Nhóm step chạy trên 1 máy (runner). Các job **song song** mặc định |
| **Step** | 1 lệnh shell (`run`) hoặc 1 action dựng sẵn (`uses`) |
| **Runner** | Máy ảo chạy job (`ubuntu-latest`) — luôn sạch, không giữ gì từ lần trước |
| **Action** | Gói tái sử dụng, vd `actions/checkout@v4`, `actions/setup-python@v5` |

### Lint vs Test — hai việc khác nhau
- **Ruff** = phân tích **tĩnh** (không chạy code): bắt lỗi cú pháp, import thừa, thứ tự import, bẫy bug phổ biến (`B`), lỗi bảo mật kiểu bandit (`S`), `print` sót lại (`T20`). Cực nhanh (viết bằng Rust), thay thế flake8 + isort + pyupgrade + bandit trong một công cụ.
- **Pytest** = chạy code thật với dữ liệu giả, kiểm tra **hành vi**. Lint không bắt được logic sai; test không bắt được style/import rác. Cần cả hai.

## 🛠 Thiết kế workflow & lý do từng quyết định

### 1. Trigger có lọc `paths`
```yaml
on:
  pull_request:
    branches: [main, develop]
    paths: ["backend/**", ".github/workflows/backend-ci.yml"]
  push:
    branches: [main, develop]
    paths: [...]
```
- **PR** là cổng chính. **Push** vào `main/develop` là lưới an toàn (merge commit, admin push bỏ qua review).
- `paths:` → PR chỉ sửa frontend **không** chạy pipeline Python, đỡ tốn phút CI.
- Có cả đường dẫn của chính file workflow, để sửa CI thì CI tự chạy kiểm tra lại chính nó.

> ⚠️ **Cạm bẫy khi bật Branch Protection:** nếu đặt check này là "required" mà workflow bị `paths` bỏ qua, PR frontend-only sẽ kẹt ở trạng thái "Expected — waiting for status". Khi đó cần cách xử lý riêng (workflow rỗng cùng tên job, hoặc bỏ `paths`). Hiện chưa bật required nên chưa gặp.

### 2. `concurrency` + `cancel-in-progress`
```yaml
concurrency:
  group: backend-ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```
Push thêm commit vào cùng PR → hủy lần chạy cũ. Chạy tiếp cho code đã bị thay thế chỉ phí tài nguyên.

### 3. `defaults.run.working-directory: backend`
Mọi lệnh `run` tự `cd backend`. Nhưng `actions/setup-python` (`uses`) **không** bị ảnh hưởng, nên `cache-dependency-path` phải ghi đường dẫn đầy đủ `backend/pyproject.toml`.

### 4. Hai job tách riêng (`lint`, `test`) chạy song song
- Lint xong trong vài giây, báo lỗi style ngay mà không phải chờ test.
- Trên PR thấy rõ **cái gì** đỏ: "Lint" hay "Test".
- Đánh đổi: cài dependencies 2 lần. Chấp nhận được vì có cache pip.

### 5. Cache pip
```yaml
- uses: actions/setup-python@v5
  with:
    python-version: "3.12"
    cache: "pip"
    cache-dependency-path: backend/pyproject.toml
```
Cache key băm từ `pyproject.toml` — đổi dependency thì cache tự làm mới. Python **3.12** khớp với `target-version = "py312"` của Ruff và image Docker.

### 6. Cài bằng `pip install -e ".[dev]"`
Dùng đúng nhóm `dev` trong `pyproject.toml` (pytest, ruff, httpx...) → **một nguồn sự thật duy nhất** cho phiên bản công cụ, CI và máy dev không lệch nhau.

### 7. Pytest lấy cấu hình từ `pyproject.toml`
`addopts` đã có `--cov=app --cov-report=term-missing --cov-report=html`, nên CI chỉ cần gõ `pytest`. Không lặp lại cờ ở hai nơi → khỏi lệch.

### 8. Upload coverage với `if: always()`
```yaml
- name: Upload coverage report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: backend-coverage-html
    path: backend/htmlcov/
    retention-days: 14
```
`if: always()` để khi test **fail**, báo cáo vẫn được upload — đúng lúc cần nó nhất để xem dòng nào chưa được phủ. `retention-days: 14` tránh artifact chiếm dung lượng mãi.

## ✅ Cách kiểm tra

**Chạy lại đúng các lệnh CI trên máy local trước khi push:**
```bash
cd backend
pip install -e ".[dev]"
ruff check app/ tests/
pytest
```
Nếu local xanh mà CI đỏ, nguyên nhân thường là: khác phiên bản Python, thiếu dependency khai báo trong `pyproject.toml` (local có sẵn do cài tay), hoặc test phụ thuộc file/biến môi trường chỉ có trên máy bạn — đúng loại lỗi mà CI sinh ra để bắt.

**Xem trên GitHub:** tạo PR có đổi `backend/**` → tab *Checks* hiện 2 job `Lint (Ruff)` và `Test (Pytest)`; mở run để tải artifact `backend-coverage-html`.

## 🔑 Bài học rút ra
1. **CI là cổng chặn tự động**, không phải thủ tục — giá trị nằm ở chỗ nó chạy trên môi trường sạch.
2. **Một nguồn sự thật cho cấu hình** (`pyproject.toml`) — CI chỉ gọi lệnh, không tự định nghĩa lại luật lint hay cờ pytest.
3. **Tách job theo loại phản hồi** để lỗi nào hiện ra đúng chỗ đó và nhanh nhất có thể.
4. **Tiết kiệm tài nguyên có chủ đích:** `paths` filter + `concurrency` cancel.
5. **Artifact cho trường hợp fail** (`if: always()`) — thứ cần để gỡ lỗi phải còn đó khi mọi thứ đỏ.
