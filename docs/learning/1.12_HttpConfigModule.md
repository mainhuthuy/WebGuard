# Task 1.12 — `HttpConfigModule` (Hành vi HTTP/HTTPS của server)

> **Mục tiêu:** Xây dựng module thứ 7 (module cuối cùng của `full`), kiểm tra **cách server xử lý giao thức HTTP** ở tầng thấp hơn nội dung trang: có ép HTTPS không, có bật phương thức nguy hiểm không, có khai báo kênh báo lỗi bảo mật không, và có lỗi redirect mở (open redirect) không.

---

## 📚 Lý thuyết: 4 kiểm tra, 4 kỹ thuật HTTP khác nhau

Khác với các module trước (chủ yếu `GET` rồi đọc response), module này cần **4 cách tương tác HTTP khác nhau** với cùng một mục tiêu — minh họa rằng `httpx.AsyncClient` làm được nhiều hơn `client.get()`.

### 1. Ép HTTPS — gọi sang cổng 80 (HTTP thuần)

Muốn biết server có "ép" HTTPS không, phải **tự đi vòng** sang bản HTTP của URL, vì URL gốc người dùng nhập có thể đã là `https://`:
```python
@staticmethod
def _plain_http_url(url: str) -> str:
    parsed = urlparse(url)
    netloc = parsed.netloc if parsed.scheme == "http" else (parsed.hostname or "")
    return f"http://{netloc}/"
```
Lưu ý: nếu target gốc dùng cổng khác 443 (`https://example.com:8443`), hàm **bỏ cổng** khi dựng URL HTTP — vì cổng HTTPS tùy biến không có nghĩa là cổng HTTP (80) cũng tùy biến theo; ta luôn thử cổng 80 mặc định trừ khi chính target đã là `http://` (khi đó giữ nguyên `netloc` gốc, gồm cả cổng nếu có).

```python
async def _check_https_redirect(self, client, url):
    target = self._plain_http_url(url)
    try:
        response = await client.get(target)
    except httpx.HTTPError:
        return None   # Cổng 80 ĐÓNG = tốt (server chỉ phục vụ HTTPS, không có gì để hạ cấp)
    location = response.headers.get("location", "")
    if response.status_code in REDIRECT_STATUSES and location.lower().startswith("https://"):
        return None   # Có redirect đúng sang HTTPS = tốt
    return self._finding("https_not_enforced", "high", ...)
```
Điểm hay: **lỗi kết nối ở đây lại là tín hiệu TỐT** — ngược với mọi module khác (nơi lỗi kết nối thường nghĩa là "có vấn đề"). Một server chỉ mở cổng 443, đóng hẳn cổng 80, là cấu hình an toàn hơn server mở cổng 80 rồi mới redirect.

### 2. TRACE — phương thức HTTP hiếm dùng, có thể bị lạm dụng

`TRACE` là phương thức HTTP gốc dùng để **debug**: server phải echo (gửi lại nguyên văn) chính request nó nhận được, bao gồm mọi header. Nếu bật trên production, kết hợp với một lỗ hổng XSS khác, kẻ tấn công có thể dùng kỹ thuật **Cross-Site Tracing (XST)** để đọc header `httpOnly` cookie gián tiếp (gửi request TRACE qua JavaScript, đọc lại cookie từ nội dung response được echo về — vì `document.cookie` bị chặn bởi `HttpOnly` nhưng response body của TRACE thì không):
```python
response = await client.request("TRACE", url)
if response.status_code == 200 and "trace" in response.text[:4096].lower():
    return self._finding("http_trace_enabled", "medium", ...)
```
`client.request(method, url)` là dạng tổng quát của `client.get()`/`client.post()` — dùng khi cần một phương thức HTTP không có hàm tiện ích riêng.

### 3. OPTIONS — hỏi thẳng server "tôi được làm gì"

`OPTIONS` là phương thức dùng để **hỏi** server chấp nhận những phương thức nào trên một URL, trả lời qua header `Allow`:
```python
response = await client.request("OPTIONS", url)
allow = response.headers.get("allow", "")
methods = {m.strip().upper() for m in allow.split(",") if m.strip()}
risky = [m for m in ("PUT", "DELETE", "CONNECT") if m in methods]
```
`PUT`/`DELETE` cho phép **tạo/sửa/xóa tài nguyên** trực tiếp qua HTTP — nếu không được xác thực/phân quyền đúng cách (lỗi cấu hình phổ biến ở WebDAV, một số REST framework mặc định), đây là cách chiếm quyền ghi vào server mà không cần khai thác gì phức tạp. `CONNECT` dùng để tạo đường hầm (tunnel) — mở trên server web công khai có thể bị lợi dụng làm proxy trung gian.

### 4. `security.txt` — kênh báo lỗi chính thức (RFC 9116)

Đây là kiểm tra duy nhất trong module **không phải lỗ hổng** mà là **thiếu thực hành tốt**: file `/.well-known/security.txt` là chuẩn chính thức (RFC 9116) để site công bố địa chỉ liên hệ cho nhà nghiên cứu bảo mật muốn báo lỗi có trách nhiệm:
```
Contact: mailto:security@example.com
Expires: 2026-12-31T23:59:59Z
```
```python
target = f"{parsed.scheme}://{parsed.netloc}/.well-known/security.txt"
response = await client.get(target)
if response.status_code == 200 and "contact:" in response.text[:8192].lower():
    return None
return self._finding("security_txt_missing", "low", ...)
```
Severity `low` vì không có file này **không** phải lỗ hổng kỹ thuật — chỉ là thiếu một kênh giao tiếp hữu ích. Giống `/.env`/`/.git` ở `InformationModule` (1.5), kiểm tra này cũng cần tránh bẫy "soft-404" (site trả 200 cho mọi URL): chỉ coi là có khi nội dung thật sự chứa `Contact:`.

## 📚 Kiểm tra thứ 5 (thêm sau): Open Redirect — chủ động, rủi ro thấp

> Cũng như `ContentModule` (1.11), sau khi cân nhắc ranh giới giữa "audit cấu hình" và "tấn công thật", kiểm tra chủ động duy nhất được thêm vào module này là **dò open redirect** — không injection, không brute-force.

### Open Redirect là gì?

Nhiều trang có tham số dùng để "quay lại đúng chỗ" sau khi đăng nhập/đăng xuất: `?next=/dashboard`, `?redirect=/home`. Nếu server **không kiểm tra** giá trị này có phải đường dẫn nội bộ hay không mà chuyển hướng thẳng, kẻ tấn công tạo được link:
```
https://your-trusted-bank.com/login?next=https://evil-phishing-site.com
```
Link trông như trỏ tới site thật (đúng domain!), nhưng sau khi qua bước xác thực trên domain thật, nạn nhân bị **chuyển hướng sang site giả mạo** — kỹ thuật này thường dùng để qua mặt bộ lọc link trong email hoặc tạo lòng tin giả trước khi lừa đảo.

### Dò an toàn: domain `.invalid` không bao giờ phân giải được

Điểm mấu chốt để kiểm tra này **an toàn**: giá trị "mồi" dùng để dò phải (1) trông đủ giống một địa chỉ thật để lộ ra lỗi, nhưng (2) **không bao giờ** thực sự tải được gì nếu có ai/cái gì vô tình theo redirect đó.

RFC 2606 dành riêng TLD `.invalid` cho đúng mục đích này — đảm bảo **không bao giờ được đăng ký, không bao giờ phân giải DNS**:
```python
OPEN_REDIRECT_MARKER = "https://webguard-redirect-check.invalid/"
```
Và quan trọng hơn: `httpx.AsyncClient` mặc định **không tự theo redirect** (project chủ động giữ cấu hình này ở mọi module, xem `1.5`) — nên dù server có trả `Location: https://webguard-redirect-check.invalid/`, scanner **chỉ đọc header đó**, không có request thứ hai nào được gửi tới domain `.invalid` cả.

### Thử lần lượt các tên tham số thường gặp

```python
REDIRECT_PARAM_NAMES = ("redirect", "redirect_uri", "redirect_url", "url", "next", "return",
                         "returnto", "return_url", "continue", "dest", "destination", "r")

async def _check_open_redirect(self, client, url):
    separator = "&" if "?" in url else "?"
    for param in REDIRECT_PARAM_NAMES:
        probe = f"{url}{separator}{urlencode({param: OPEN_REDIRECT_MARKER})}"
        response = await client.get(probe)
        location = response.headers.get("location", "")
        if response.status_code in REDIRECT_STATUSES and "webguard-redirect-check.invalid" in location:
            return self._finding("open_redirect", "medium", ...)
    return None
```
Dừng ngay khi tìm thấy 1 tham số lỗi (không cần thử hết 12 tên) — giữ số request tới target ở mức thấp nhất cần thiết. Đây vẫn chỉ là **GET với query string thêm vào** — hoàn toàn giống một lượt truy cập bình thường có tham số, không khác gì về bản chất với việc `InformationModule` thử nhiều đường dẫn khác nhau.

### Kết quả kiểm chứng

`tests/unit/test_http_config.py` mô phỏng server "dính" open redirect trên đúng 1 tham số, các tham số còn lại trả về redirect hợp lệ (không mắc bẫy):

```python
async def test_open_redirect_via_common_param_is_reported() -> None:

```

## 💻 Vòng quét chính — 5 kiểm tra độc lập, không chia sẻ response

```python
async def scan(self, url: str, **kwargs) -> list:
    async with httpx.AsyncClient(timeout=HTTP_TIMEOUT) as client:
        results = [
            await self._check_https_redirect(client, url),
            await self._check_trace(client, url),
            await self._check_allowed_methods(client, url),
            await self._check_security_txt(client, url),
            await self._check_open_redirect(client, url),
        ]
    return [r for r in results if r]   # lọc bỏ None (kiểm tra không phát hiện gì)
```
Khác với `CORSModule` (1.6, tái sử dụng response giữa các check), 5 check ở đây **độc lập hoàn toàn** — mỗi hàm tự `try/except httpx.HTTPError` riêng (lỗi mạng ở 1 check không ảnh hưởng 4 check còn lại), và không có check nào phụ thuộc kết quả của check khác.

## 🔑 Takeaway

1. **`httpx.AsyncClient` không chỉ có `.get()`/`.post()`** — `.request(method, url)` dùng cho mọi phương thức HTTP ít gặp (`TRACE`, `OPTIONS`, `PATCH`...).
2. **Đôi khi "không kết nối được" lại là tín hiệu tốt** — cổng 80 đóng hẳn an toàn hơn cổng 80 mở rồi redirect.
3. **TLD `.invalid` (RFC 2606)** là "mồi" an toàn tiêu chuẩn cho mọi kiểm tra cần một địa chỉ bên ngoài không có thật — kết hợp với việc không tự theo redirect, đảm bảo kiểm tra chủ động vẫn không chạm tới bất kỳ hệ thống thứ ba nào.
4. **Không phải mọi finding đều là lỗ hổng** — `security_txt_missing` là ví dụ về "thiếu thực hành tốt", severity thấp, khác về bản chất với các finding mang tính kỹ thuật tấn công trực tiếp.
