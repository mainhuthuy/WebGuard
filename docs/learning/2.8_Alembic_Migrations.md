# Task 2.8 — Alembic Migrations (Quản lý phiên bản Database)

> **Mục tiêu:** Tự động hóa việc quản lý cấu trúc bảng (schema) của cơ sở dữ liệu SQLite thông qua **Alembic**, hỗ trợ nâng cấp (upgrade) và hạ cấp (downgrade) cấu trúc bảng mà không làm mất dữ liệu người dùng.

---

## 🧭 1. Alembic là gì & Tại sao cần Migration?

### Vấn đề thực tế trong phát triển phần mềm:
1. **`create_all()` là "dùng 1 lần rồi bỏ":** Hàm `Base.metadata.create_all()` chỉ tạo bảng khi bảng **hoàn toàn chưa tồn tại**. Nếu sau này ta muốn thêm cột, đổi kiểu dữ liệu, hoặc tạo index mới thì `create_all()` hoàn toàn không có tác dụng.
2. **Nỗi sợ mất dữ liệu:** Nếu không dùng migration, cách duy nhất để cập nhật bảng là... **xóa file SQLite đi tạo lại**, đồng nghĩa với việc mất trắng toàn bộ dữ liệu lịch sử quét của khách hàng!
3. **Làm việc nhóm (Team Collaboration):** Khi nhiều lập trình viên cùng thêm/sửa bảng, ai sẽ là người chạy câu lệnh SQL để cập nhật database của cả đội?

👉 **Alembic chính là "Git dành cho Database"**: Mỗi lần thay đổi schema sẽ được lưu thành 1 file script (gọi là một **Revision**). Khi deploy lên server hoặc kéo code mới về, chỉ cần gõ 1 lệnh là database tự động cập nhật đúng phiên bản mới nhất!

## 💻 3. Các điểm kỹ thuật quan trọng trong cấu hình

### 3.1. Kết nối động với `config.py` và `models` trong `env.py`:
File `app/db/migrations/env.py` được tùy biến để:
- Tự động lấy URL từ `app.core.get_settings().DB_URL`.
- Nạp toàn bộ metadata của `Base` từ `app.models`:
```python
from app.core import get_settings
from app.db.session import Base
import app.models  # Nạp tất cả model để metadata nhận diện

target_metadata = Base.metadata
```

### 3.2. Cấu hình `render_as_batch=True` cho SQLite:
SQLite là một cơ sở dữ liệu rất nhẹ và có một hạn chế lớn: **Không hỗ trợ đầy đủ lệnh `ALTER TABLE`** (ví dụ không thể drop column hoặc đổi kiểu column trực tiếp).
- Cờ `render_as_batch=True` kích hoạt chế độ **Batch Operations** của Alembic:
- Khi cần sửa bảng, Alembic sẽ:
  1. Tạo một bảng tạm mới với cấu trúc mới.
  2. Copy toàn bộ dữ liệu từ bảng cũ sang bảng mới.
  3. Xóa bảng cũ và đổi tên bảng mới thành bảng cũ.
  👉 Hoàn toàn tự động và an toàn tuyệt đối!

### 3.3. Alembic và `init_db()` cùng tồn tại — chúng không giống nhau

Project có **hai** cách tạo/cập nhật schema:

| | `init_db()` (`db/session.py`) | Alembic (`alembic upgrade head`) |
|---|---|---|
| Khi nào chạy | Tự động mỗi lần khởi động server (trong `lifespan`) | Chạy tay khi triển khai |
| Việc làm | `Base.metadata.create_all()` — chỉ tạo bảng **chưa có** | Áp dụng các revision theo thứ tự, có `downgrade` |
| Ghi nhớ phiên bản | Không | Có (bảng `alembic_version`) |

Hệ quả khi thêm cột `mode` (Sprint 3): `create_all` **không** thêm cột vào bảng đã tồn tại, nên một file `webguard.db` tạo từ trước sẽ thiếu cột và `POST /scan` lỗi `no column named mode`. Cách project xử lý:

1. Viết migration Alembic `9c3e1f7a2b64` (đường chính thống, có `downgrade`), dùng `batch_alter_table` + `server_default='full'` để các dòng cũ có giá trị.
2. Thêm hàm `_upgrade_legacy_schema()` trong `init_db()`: nếu bảng `scans` thiếu cột `mode` thì chạy `ALTER TABLE scans ADD COLUMN mode ... DEFAULT 'full'` — để DB dev cũ tự nâng cấp khi khởi động mà không phải nhớ chạy Alembic. Hàm này idempotent (chạy nhiều lần vẫn an toàn) và được test (`test_legacy_database_is_upgraded_with_mode_column`).

> ⚠️ Cách tạm này chỉ phù hợp giai đoạn phát triển. Về lâu dài nên bỏ `create_all` khỏi lúc khởi động và để Alembic là **nguồn duy nhất** thay đổi schema (hai cơ chế song song dễ lệch nhau). Khi dùng Docker (Sprint 4) nên chạy `alembic upgrade head` ở bước khởi động container.

## 🛠️ 4. Các lệnh Alembic thường dùng nhất

| Lệnh | Ý nghĩa |
|---|---|
| `alembic revision --autogenerate -m "tên_mô_tả"` | Tự động so sánh code Python Models với Database và sinh file migration |
| `alembic upgrade head` | Áp dụng tất cả các migration mới nhất vào Database |
| `alembic downgrade -1` | Lùi lại 1 phiên bản migration gần nhất (Undo) |
| `alembic current` | Xem database hiện tại đang ở revision nào |
| `alembic history` | Xem toàn bộ lịch sử các lần migration |

## 🔑 Tóm tắt cốt lõi (Takeaway)

1. **Migration** giúp thay đổi cấu trúc database có kiểm soát phiên bản, không bao giờ phải xóa database làm lại từ đầu.
2. **`render_as_batch=True`** là "chìa khóa vàng" khi dùng Alembic với SQLite.
3. **`alembic_version`** là một bảng đặc biệt do Alembic tự sinh trong DB để ghi nhớ revision hiện tại là gì.
