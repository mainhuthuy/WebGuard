> **Mục tiêu:** Xây dựng endpoint REST cho phép truy vấn lại toàn bộ thông tin chi tiết của một phiên quét bất kỳ (URL mục tiêu, trạng thái, thời gian, danh sách lỗ hổng và điểm số an ninh).

> 📌 Thời gian (`created_at`, `completed_at`) trả về là **UTC không kèm offset** (vd `2026-10-01T03:05:08.19`), vì SQLite không lưu múi giờ (xem 2.7). Client phải hiểu chúng là UTC — frontend thêm hậu tố `Z` trước khi parse.

## 🧭 1. Tại sao cần API này khi đã có SSE ở Task 2.3?

SSE và REST GET phục vụ **hai nhu cầu khác nhau hoàn toàn**:

| | SSE (Task 2.3) | REST GET (Task 2.4) |
|---|---|---|
| **Khi nào dùng?** | **Trong lúc đang quét** (0% → 100%) | **Sau khi quét xong** hoặc bất kỳ lúc nào |
| **Kết nối** | Duy trì mở liên tục (long-lived) | Gửi 1 lần, nhận 1 lần, ngắt ngay (stateless) |
| **Mục đích** | Hiển thị thanh tiến trình thời gian thực | Xem lại báo cáo, xuất file, tra cứu lịch sử |
| **Ví dụ thực tế** | YouTube: Thanh loading khi upload video | YouTube: Xem lại video đã upload xong |

### Các tình huống cần GET:
1. Người dùng **F5 reload** trang sau khi quét xong → Cần lấy lại kết quả.
2. Vào tab **Lịch sử quét (History)** bấm xem một báo cáo cũ.
3. Hệ thống cần **xuất báo cáo PDF/HTML** (Task 2.5 sắp tới).
4. Các công cụ bên ngoài (CI/CD pipeline) gọi API để kiểm tra kết quả quét tự động.

## 📚 2. Nguyên tắc thiết kế RESTful: Tài nguyên và HTTP Method

### REST là gì?
REST (Representational State Transfer) là một quy ước thiết kế API, trong đó mỗi **URL đại diện cho một tài nguyên** (resource), và ta dùng **HTTP Method** để chỉ định hành động:

| HTTP Method | Ý nghĩa | Ví dụ trong WebGuard |
|---|---|---|
| `POST` | **Tạo mới** tài nguyên | `POST /api/v1/scan` → Tạo lượt quét mới |
| `GET` | **Đọc** / lấy thông tin | `GET /api/v1/scan/{id}` → Xem kết quả quét |
| `PUT` | **Cập nhật** toàn bộ | (Chưa dùng trong WebGuard) |
| `DELETE` | **Xóa** tài nguyên | `DELETE /api/v1/history/{id}` → Xóa một lượt quét khỏi lịch sử (Task 2.11) |

Với task này, ta dùng `GET /api/v1/scan/{scan_id}` — nghĩa là: **"Lấy thông tin của tài nguyên Scan có mã định danh là `scan_id`"**.

## 📚 3. Idempotency (Tính bình đẳng): Tại sao GET an toàn?

Một khái niệm quan trọng trong thiết kế API:
- **GET** là phương thức **idempotent** (bình đẳng) — gọi 1 lần hay gọi 100 lần đều trả về cùng kết quả và **không thay đổi dữ liệu** trên server.
- **POST** là phương thức **non-idempotent** — mỗi lần gọi có thể tạo ra một tài nguyên mới khác nhau.

👉 Đây là lý do tại sao trình duyệt cho phép F5 reload trang GET thoải mái, nhưng lại hỏi xác nhận *"Bạn có muốn gửi lại form?"* khi reload trang POST.

## 💻 4. Thiết kế Response Schema

File: [`backend/app/schemas/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/schemas/scan.py)

```python
class ScanDetailResponse(BaseModel):
    """Chi tiết đầy đủ thông tin và kết quả của một phiên quét."""

    scan_id: str              # Mã UUID duy nhất
    target_url: str           # URL đã quét
    mode: ScanMode            # quick / full (chế độ quét đã dùng)
    status: ScanStatus        # pending / running / completed / failed / cancelled
    created_at: datetime      # Thời điểm tạo
    completed_at: datetime | None  # Thời điểm hoàn thành (None nếu chưa xong)
    total_findings: int       # Số lỗ hổng phát hiện
    findings: list[Finding]   # Danh sách chi tiết từng lỗ hổng
    scoring: ScoringResult | None  # Điểm số (None nếu chưa tính)
```

### Tại sao `completed_at` và `scoring` có thể là `None`?
Vì khi lượt quét mới được tạo (`PENDING`) hoặc đang chạy (`RUNNING`), chưa có thời gian hoàn thành và chưa tính điểm. API phải phản ánh đúng trạng thái thực tế:
- **Pending:** `completed_at=null, scoring=null, findings=[]`
- **Completed:** `completed_at="2026-09-16T12:00:10Z", scoring={score: 85, grade: "B"}, findings=[...]`

## 💻 5. Code Endpoint

File: [`backend/app/api/v1/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/api/v1/scan.py)

```python
@router.get("/{scan_id}", response_model=ScanDetailResponse, status_code=status.HTTP_200_OK)
async def get_scan_result(scan_id: str, db: Session = Depends(get_db)) -> ScanDetailResponse:
    # 0. (Hiện tại) Ưu tiên đọc từ DATABASE qua ScanService; nếu có thì dựng response từ
    #    ScanModel + FindingModel (findings, score/grade -> ScoringResult, mode) rồi return.
    scan = scan_service.get_scan(db, scan_id)
    if scan:
        ...

    # Các bước dưới đây là phương án DỰ PHÒNG từ bộ nhớ đệm `scan_jobs`:
    # 1. Kiểm tra scan_id tồn tại
    if scan_id not in scan_jobs:
        raise ScanNotFoundException(scan_id=scan_id)

    job = scan_jobs[scan_id]
    findings = job.get("findings") or []
    scoring_data = job.get("scoring")

    # 2. Đóng gói scoring (chỉ khi quét hoàn tất)
    scoring_result = None
    if isinstance(scoring_data, dict) and "score" in scoring_data:
        scoring_result = ScoringResult(
            score=scoring_data["score"],
            grade=scoring_data["grade"],
            total_findings=scoring_data.get("total_findings", len(findings)),
        )

    # 3. Trả về kết quả
    return ScanDetailResponse(
        scan_id=scan_id,
        target_url=job["target_url"],
        status=job["status"],
        created_at=job["created_at"],
        completed_at=job.get("completed_at"),
        total_findings=len(findings),
        findings=findings,
        scoring=scoring_result,
    )
```

## 🔑 Tóm tắt cốt lõi (Takeaway)

1. **REST GET vs SSE:** SSE dùng để xem trực tiếp (real-time), GET dùng để tra cứu lại (on-demand). Hai cái bổ trợ nhau.
2. **RESTful Design:** URL = tài nguyên, HTTP Method = hành động. `GET /scan/{id}` = "đọc thông tin lượt quét này".
3. **Idempotency:** GET an toàn vì gọi bao nhiêu lần cũng không thay đổi dữ liệu.
4. **Nullable Fields:** `completed_at` và `scoring` có thể là `None` để phản ánh đúng trạng thái vòng đời (pending → running → completed).
