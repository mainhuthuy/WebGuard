# Task 4.2 — Frontend Dockerfile (Multi-stage + Nginx)

> **Mục tiêu:** Đóng gói frontend thành image chỉ chứa **đúng static bundle** (không Node, không `node_modules`), phục vụ bởi Nginx không-root, với các security header mà chính WebGuard dùng để chấm điểm website khác.
>
> File Dockerfile gốc **đã** multi-stage (`build` → `production`) và **đã** dùng `nginx:alpine` — phần khung đúng ngay từ đầu. Nhưng khi build-test thật (không chỉ đọc code), lộ ra **4 lỗi** — tất cả đều là loại lỗi "đọc code thấy hợp lý, chạy mới biết sai".

---

## 📚 Lý thuyết: Vì sao frontend "multi-stage" còn triệt để hơn backend

Ở backend (`4.1`), multi-stage tách "môi trường cài dependency" khỏi "môi trường chạy app" — nhưng cả hai vẫn là Python. Ở frontend, hai môi trường **khác hẳn công nghệ**:

```dockerfile
FROM node:22-alpine AS build       # Cần Node.js, npm, toàn bộ node_modules (~vài trăm MB) để BIÊN DỊCH
RUN npm run build                   # tsc -b (type-check) + vite build -> dist/ (vài trăm KB)

FROM nginx:alpine AS production     # KHÔNG cần Node gì cả để PHỤC VỤ file tĩnh
COPY --from=build /app/dist /usr/share/nginx/html
```
Sau khi build xong, `dist/` chỉ là HTML/CSS/JS thuần — phục vụ chúng không cần Node.js, không cần bất kỳ package nào trong `node_modules`. Đây là multi-stage build "điển hình" nhất: base image stage sau (`nginx:alpine`, ~40MB) **nhỏ hơn hẳn** base image stage build (`node:22-alpine` + `node_modules`, có thể vài trăm MB). Kết quả: image cuối **95.9MB** — gần như toàn bộ là nginx + bundle, không mang theo bất kỳ dấu vết nào của Node.

## 🐞 Bug #1 (nghiêm trọng nhất): `docker-compose.yml` production thực ra chạy... Vite dev server

Dockerfile có 3 stage theo thứ tự: `build` → `production` → `dev`. `docker-compose.yml` (bản "production") build frontend **không khai báo `target:`**:
```yaml
frontend:
  build:
    context: ../frontend
    dockerfile: Dockerfile
    # (không có target)
```
**Quy tắc Docker ít ai để ý:** khi không chỉ định `--target`/`target:`, Docker build **stage cuối cùng khai báo trong file**, không phải stage "hợp lý nhất". Stage cuối cùng ở đây là `dev` (dùng cho `docker-compose.dev.yml`, có `CMD ["npm", "run", "dev", ...]`) — nghĩa là **compose "production" đã luôn build và chạy nhầm sang stage dev** kể từ khi 2 file này được viết, mà không ai phát hiện vì chưa từng `docker compose up` thật để kiểm tra.

```bash
$ docker compose build frontend
#5 [dev 1/5] FROM node:22-alpine     # ← build nhầm "dev", không phải "production"!
```

**Sửa:** khai báo tường minh, giống hệt cách `docker-compose.dev.yml` đã làm đúng cho stage `dev` của nó:
```yaml
frontend:
  build:
    context: ../frontend
    dockerfile: Dockerfile
    target: production   # <-- bắt buộc, nếu không Docker build stage CUỐI CÙNG trong file
```

> 🔑 **Bài học:** một Dockerfile nhiều stage **không tự nhiên "biết" stage nào là production** — người viết `docker-compose.yml`/lệnh build phải nói rõ bằng `target`. Không khai báo không phải là lỗi cú pháp (Docker build vẫn chạy "thành công"), nên lỗi loại này **im lặng hoàn toàn** cho tới khi ai đó so sánh kết quả thực tế với kỳ vọng.

## 🐞 Bug #2: `add_header` không kế thừa vào location đã tự khai `add_header`

Thêm 6 header bảo mật (CSP, `X-Content-Type-Options`, `X-Frame-Options`...) — đúng những header mà `HeadersModule` (`1.2`) của chính dự án này chấm điểm site khác — bằng cách đặt `add_header` ở cấp `server {}`, tưởng rằng mọi `location` bên trong tự động thừa hưởng. Build và `curl` thử thì **toàn bộ 6 header biến mất** ở `location /` và `location /assets/`.

**Nguyên nhân — một "gotcha" kinh điển của Nginx:** `add_header` không hoạt động như CSS (kế thừa rồi override). Quy tắc thật: **nếu một `location` tự khai bất kỳ `add_header` nào, nó bỏ qua HOÀN TOÀN danh sách `add_header` kế thừa từ `server`/`http`** — không merge, không cộng dồn:
```nginx
server {
    add_header X-Frame-Options "SAMEORIGIN" always;   # (A)

    location / {
        add_header Cache-Control "no-cache";           # (B) — có add_header riêng
        # => (A) bị BỎ QUA hoàn toàn ở location này, không phải "cộng thêm (B)"
    }
}
```
Hai `location` của dự án (`/` phục vụ `index.html` với `Cache-Control: no-cache`, `/assets/` phục vụ bundle với `Cache-Control: ...immutable`) **đều** tự khai `add_header` riêng cho cache — nên cả hai đều vô tình xoá sạch 6 header bảo mật kế thừa từ `server`.

**Sửa:** tách 6 header bảo mật ra một file riêng (`security-headers.conf`), rồi `include` tường minh vào **từng** `location` cần nó:
```nginx
location / {
    add_header Cache-Control "no-cache";
    include /etc/nginx/security-headers.conf;
}
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    include /etc/nginx/security-headers.conf;
}
```
File này **không** đặt trong `/etc/nginx/conf.d/` dù đó là nơi "tự nhiên" nhất — vì nginx base image có sẵn `include /etc/nginx/conf.d/*.conf;` ở cấp `http`, tự động nạp **mọi** file `.conf` trong thư mục đó như một config độc lập. Một file chỉ có vài dòng `add_header` (không bọc trong `server {}`) không phải là thứ thư mục này dành cho — đặt ngoài `conf.d/` (`/etc/nginx/security-headers.conf`) và chỉ nạp nó đúng nơi cần bằng `include` tường minh, tránh mọi nhập nhằng về việc nó bị nạp thêm một lần nữa theo kiểu ẩn.

> 🔑 **Bài học:** đọc tài liệu Nginx về `add_header` sẽ thấy đúng câu "directives are inherited from the previous level **only if** there are no add_header directives at the current level" — rất dễ bỏ qua khi lướt qua, chỉ lộ ra khi `curl -I` kiểm tra thật.

## 🐞 Bug #3: Healthcheck dùng `localhost`, nhưng container resolve ra IPv6 trước

```dockerfile
HEALTHCHECK CMD wget --spider http://localhost:8080/ || exit 1
```
Container khởi động "healthy"... rồi mãi ở trạng thái `health: starting`, không bao giờ chuyển `healthy`. Kiểm tra tay bằng `docker exec`:
```
$ wget --spider http://localhost:8080/
wget: can't connect to remote host: Connection refused
$ wget --spider http://127.0.0.1:8080/
(thành công)
```
**Nguyên nhân:** `/etc/hosts` trong Alpine liệt kê cả `::1 localhost` lẫn `127.0.0.1 localhost`; thư viện phân giải tên (`musl libc`) trả `::1` (IPv6) **trước** `127.0.0.1`. `busybox wget` thử đúng địa chỉ đầu tiên trả về (IPv6) — nhưng `nginx.conf` chỉ `listen 8080;` (ngầm định là **IPv4-only** `0.0.0.0:8080`), không có `listen [::]:8080;` — nên kết nối IPv6 bị từ chối ngay, và `wget` **không tự thử lại** bằng địa chỉ IPv4 tiếp theo.

**Sửa:** chỉ định thẳng `127.0.0.1` thay vì `localhost`, bỏ qua hoàn toàn bước phân giải DNS/hosts có thể trả nhầm thứ tự:
```dockerfile
CMD wget --quiet --tries=1 --spider http://127.0.0.1:8080/ || exit 1
```

**Vì sao healthcheck của backend (`4.1`) KHÔNG gặp lỗi này dù cũng viết `http://localhost:8000`?** Vì nó dùng `urllib.request.urlopen`, mà bên dưới gọi `socket.create_connection()` — hàm này **tự động thử lần lượt từng địa chỉ** `getaddrinfo()` trả về cho tới khi một địa chỉ kết nối được, thay vì chỉ thử đúng 1 địa chỉ đầu tiên rồi bỏ cuộc như `wget`. Đã kiểm tra lại bằng tay: container backend (Debian) cũng trả `::1` trước `127.0.0.1` y hệt — chỉ là Python "chịu khó" thử tiếp, còn busybox `wget` thì không.

> 🔑 **Bài học:** hai công cụ tưởng "làm cùng một việc" (gửi 1 HTTP request) có thể khác nhau ở hành vi **không được quảng cáo** (có tự fallback qua các địa chỉ hay không) — chỉ lộ ra khi cùng một kiểu cấu hình (`listen` IPv4-only + `localhost` đa nghĩa) chạy qua cả hai công cụ và cho hai kết quả khác nhau.

## 🐞 Bug #4 (tiềm ẩn, chưa sửa — chỉ ghi nhận): nginx cache DNS của `backend` chỉ một lần

`proxy_pass http://backend:8000;` (tên service Docker Compose) được Nginx phân giải DNS **một lần lúc khởi động/reload**, rồi dùng mãi địa chỉ IP đó. Nếu container `backend` bị tạo lại (crash, redeploy) và nhận **IP nội bộ mới** trong mạng Docker, Nginx **không tự re-resolve** — mọi request proxy sẽ lỗi cho tới khi chính Nginx được khởi động lại. `depends_on: condition: service_healthy` (đã có sẵn) che được tình huống khởi động lần đầu, nhưng không che được backend bị restart sau đó.

**Chưa sửa trong lần này** vì nằm ngoài phạm vi "đóng gói Dockerfile" — thuộc về cấu hình resilience của reverse proxy (đổi `proxy_pass` sang dùng biến + `resolver 127.0.0.11;`, để Nginx phân giải lại theo từng request). Ghi nhận ở đây để không quên.

## 💻 Dockerfile hoàn chỉnh

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine AS production
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY security-headers.conf /etc/nginx/security-headers.conf
RUN touch /var/run/nginx.pid \
    && chown -R nginx:nginx /var/cache/nginx /var/run/nginx.pid /usr/share/nginx/html
USER nginx
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s --start-period=5s --retries=3 \
    CMD wget --quiet --tries=1 --spider http://127.0.0.1:8080/ || exit 1
CMD ["nginx", "-g", "daemon off;"]

FROM node:22-alpine AS dev
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
EXPOSE 5173
CMD ["npm", "run", "dev", "--", "--host", "0.0.0.0"]
```

### Vì sao cũng chạy non-root được dễ dàng (không cần tự tạo user như backend)

`nginx:alpine` **đã sẵn** user hệ thống tên `nginx` (dùng cho worker process từ trước tới giờ, kể cả khi chạy root) — chỉ cần đổi `listen` sang cổng không đặc quyền (`8080` thay vì `80`, vì bind cổng < 1024 cần root) và `chown` đúng 3 thứ nginx cần ghi (`/var/cache/nginx`, pidfile, thư mục html) rồi `USER nginx`. Không cần `useradd` thủ công như backend.

## 🔑 Takeaway

1. **Một Dockerfile nhiều stage phải có người chỉ định rõ `target`** — nếu không, "stage cuối cùng trong file" âm thầm trở thành mặc định, có thể hoàn toàn không phải stage dành cho production.
2. **`add_header` không kế thừa khi location tự khai add_header riêng** — tách header dùng chung thành file `include` là cách tránh lỗi này tái diễn khi thêm location mới.
3. **"Cùng một việc" ở hai công cụ khác nhau có thể khác hành vi fallback** — `localhost` đa nghĩa (IPv4/IPv6) là một bẫy rất dễ gặp lại ở bất kỳ healthcheck/script nào khác.
4. **Một ứng dụng chấm điểm bảo mật nên tự đạt điểm cao trên chính nó** — các header thêm vào đây đúng là tập `HeadersModule` kiểm tra; không có lý do để website lưu trữ chính WebGuard lại thiếu những thứ nó khuyên người khác thêm vào.
5. **Phát hiện lỗi qua test thật tiếp tục hiệu quả hơn đọc lại code** — cả 3 bug sửa được trong task này đều đã "trông đúng" khi đọc lại, chỉ lộ ra khi build và gọi request thật.
