# Task 4.3 — Docker Compose: Production & Dev (Hot-reload)

> **Mục tiêu:** Có 2 file Compose dùng được **độc lập, không cần dọn tay giữa 2 lần chạy**: `docker-compose.yml` (production, dùng image đã build) và `docker-compose.dev.yml` (dev, bind-mount source để sửa code là thấy ngay, không cần build lại).
>
> Khung 2 file này **đã có sẵn** từ trước (bind-mount, lệnh `--reload`/`npm run dev`, `target: dev`) — phần việc hôm nay là build-test thật cả hai chế độ, và lộ ra 1 bug nghiêm trọng khi chạy chúng **cạnh nhau**.

---

## ✅ Phần đã đúng từ trước: Hot-reload hoạt động thật, không cần sửa gì

Thử nghiệm bằng cách sửa file thật trên máy host trong lúc container dev đang chạy:

**Backend** (bind-mount `../backend/app:/app/app`, lệnh `uvicorn --reload`):
```
# Sửa app/api/v1/health.py trên HOST, lưu file
# Log container ngay lập tức:
backend-1 | [...] app.main: Khởi động WebGuard API v0.1.0 [env=development, debug=True]
backend-1 | INFO: Application startup complete.
# curl /api/v1/health -> field mới xuất hiện ngay, không cần restart container
```

**Frontend** (bind-mount `../frontend/src:/app/src`, lệnh `vite --host 0.0.0.0`):
```
# Sửa pages/ScanPage.tsx trên HOST
# curl http://localhost:5173/src/pages/ScanPage.tsx -> nội dung mới trả về ngay
# (Vite transform file theo yêu cầu — không cần đợi rebuild)
```

Cả hai đều chạy đúng ngay trên Windows + Docker Desktop — môi trường vốn nổi tiếng hay gặp vấn đề với file-watching qua bind-mount (inotify của Linux bên trong container không phải lúc nào cũng nhận được sự kiện từ filesystem Windows). `uvicorn --reload` dùng thư viện `watchfiles`, Vite dùng `chokidar` — cả hai **đều có cơ chế dự phòng polling** khi phát hiện bind-mount, nên không cần tự cấu hình thêm (`WATCHFILES_FORCE_POLLING`, `usePolling`) trong trường hợp này.

> 🔑 Không phải lúc nào "tính năng nổi tiếng hay lỗi" cũng thực sự lỗi trên máy cụ thể của bạn — kiểm tra trước khi tự thêm workaround phòng hờ (thêm biến môi trường/flag không cần thiết chỉ làm rối cấu hình).

## 🐞 Bug nghiêm trọng: 2 file Compose "giẫm chân" nhau nếu không tách project name

### Phát hiện khi nào

Chạy tuần tự để test (giống một dev thực tế chuyển qua lại giữa 2 chế độ):
```bash
docker compose -f docker-compose.dev.yml up -d --build    # chạy thử dev
# ... xong việc, chuyển sang xem bản production trông thế nào ...
docker compose -f docker-compose.yml up -d                 # KHÔNG kèm --build
```
Lệnh thứ hai build lại bình thường — nhưng khi log build hiện `[dev 1/5] FROM node:22-alpine` thay vì `[production ...]`, tức là Compose **lại chạy nhầm sang stage `dev`** y hệt bug đã sửa ở `4.2`— dù lần này `docker-compose.yml` **đã có** `target: production` tường minh!

### Nguyên nhân: tên project trùng nhau

Docker Compose gắn mọi container/network/volume/**tên image** với một "project name" — mặc định là **tên thư mục** chứa lệnh `docker compose` được chạy. Cả 3 file (`docker-compose.yml`, `docker-compose.dev.yml`, `docker-compose.demo.yml`) đều nằm trong `docker/`, nên cả 3 **mặc định cùng một project name: `docker`**. Hệ quả:
- Image build ra đều tên `docker-backend` / `docker-frontend`, bất kể file nào build ra nó.
- Chạy `docker-compose.dev.yml` build ra `docker-frontend:latest` từ stage `dev`.
- Chạy tiếp `docker-compose.yml` **không có `--build`**: Compose thấy đã có sẵn image tên `docker-frontend:latest` → **tái sử dụng luôn**, không build lại — dù đó là bản `dev`, không phải `production`! `target: production` chỉ có tác dụng **khi Compose thực sự build**, không có tác dụng gì nếu nó quyết định dùng lại image cũ.

```
$ docker compose -f docker-compose.yml up -d     # (sau khi vừa chạy dev ở trên)
# Không log nào nhắc tới build -> chạy thẳng container, dùng nhầm image "dev"
```

### Sửa: khai báo `name:` tường minh cho từng file

```yaml
# docker-compose.yml
name: webguard
services: ...
```
```yaml
# docker-compose.dev.yml
name: webguard-dev
services: ...
```
```yaml
# docker-compose.demo.yml
name: webguard-demo
services: ...
```
Với `name:` tường minh, mỗi file có project name **riêng** → image tên khác nhau hẳn (`webguard-frontend` vs `webguard-dev-frontend`), network khác nhau (`webguard_default` vs `webguard-dev_default`), volume khác nhau. Không còn khả năng đụng nhau dù chạy xen kẽ bao nhiêu lần, theo thứ tự nào, có `--build` hay không.

### Kiểm chứng: lặp lại đúng kịch bản gây lỗi, với bản đã sửa

```bash
docker compose -f docker-compose.dev.yml up -d --build   # tạo image "webguard-dev-*"
docker compose -f docker-compose.yml up -d                # KHÔNG --build
```
```
Image webguard-backend Built     # <- build MỚI, đúng tên riêng, không đụng "webguard-dev-backend"
Image webguard-frontend Built
Error ... Bind for 0.0.0.0:8000 failed: port is already allocated   # (do 2 stack cùng port, chạy // nhau — không phải bug)
```
Lỗi port ở trên là **đúng kỳ vọng** khi cố tình chạy chồng 2 stack độc lập trên cùng cổng host — xác nhận ngược lại rằng chúng giờ *thực sự độc lập* (trước khi sửa, lỗi này sẽ không bao giờ xảy ra vì stack thứ hai không hề build/start riêng, chỉ lặng lẽ tái dùng container/image của stack đầu).

> 🔑 **Bài học:** `target:` trong `build:` chỉ có hiệu lực **tại thời điểm build**. Một cơ chế cache ở tầng khác (tên image trùng giữa 2 project không tên) có thể khiến bước build bị **bỏ qua hoàn toàn**, vô hiệu hoá `target:` mà không có bất kỳ cảnh báo nào. Luôn đặt `name:` tường minh khi có nhiều file Compose cho cùng một project trong cùng một thư mục.

## 📚 Lý thuyết: biến môi trường qua `docker/.env` — từ "trang trí" thành thực dùng

`docker/.env.example` đã tồn tại từ trước nhưng **không file Compose nào tham chiếu `${BIEN}` nào cả** — toàn bộ `environment:` là chuỗi cứng. Copy file này thành `.env` trước đó **không có tác dụng gì** — một dạng "nợ kỹ thuật" rất dễ bỏ sót vì không gây lỗi, chỉ đơn giản là vô dụng.

**Cách Compose tự nạp `.env`:** không cần khai báo gì đặc biệt — Compose tự tìm file `.env` trong **thư mục chạy lệnh** (ở đây là `docker/`) để thay thế mọi `${TEN_BIEN}` xuất hiện trong chính file YAML (khác với `env_file:`, vốn dùng để bơm biến *vào bên trong container*, không phải để thay thế giá trị *trong file cấu hình*).

```yaml
# docker-compose.yml
ports:
  - "${BACKEND_PORT:-8000}:8000"     # ${VAR:-default}: dùng default nếu VAR chưa đặt
environment:
  - WEBGUARD_CORS_ORIGINS=${WEBGUARD_CORS_ORIGINS:-*}
```
Cú pháp `${VAR:-default}` nghĩa là: không có `docker/.env` (hoặc thiếu biến đó) → dùng giá trị sau dấu `:-`. Nhờ vậy file vẫn chạy đúng mặc định (`8000`, `5173`, CORS `*`) **ngay cả khi ai đó chưa từng tạo `.env`** — không bắt buộc, chỉ là tùy chọn ghi đè.

Chỉ 3 biến được đưa ra tùy biến (`BACKEND_PORT`, `FRONTEND_PORT`, `WEBGUARD_CORS_ORIGINS`) — không phải mọi thứ. `WEBGUARD_ENV`/`WEBGUARD_DEBUG`/`WEBGUARD_DB_URL` **cố tình giữ cứng** trong `docker-compose.yml`, vì chính sự khác biệt của 3 giá trị này so với bản dev là điều **định nghĩa** đây là file "production" — cho phép ghi đè chúng sẽ xoá mất ranh giới đó.

### Kiểm chứng

```bash
$ docker compose -f docker-compose.yml config | grep published
published: "8000"      # mặc định, không có .env

$ printf 'BACKEND_PORT=18000\nFRONTEND_PORT=18173\nWEBGUARD_CORS_ORIGINS=https://example.com\n' > .env
$ docker compose -f docker-compose.yml config | grep -E "published|CORS_ORIGINS"
WEBGUARD_CORS_ORIGINS: https://example.com
published: "18000"
published: "18173"
```

```
  không còn tái dùng nhầm image dev                                              ✅
```

## 🔑 Takeaway

1. **"Đã có vẻ hoạt động" (hot-reload) vẫn đáng để build-test thật** — không phải vì nghi ngờ nó sai, mà vì chỉ chạy thật mới loại trừ được các vấn đề môi trường cụ thể (OS, Docker Desktop version...) mà đọc code không thấy được.
2. **Nhiều file Compose trong cùng thư mục cần `name:` tường minh** — mặc định theo tên thư mục là một "trùng lặp ẩn" chỉ lộ ra khi chạy đan xen, và hậu quả (image sai) rất khó nhận ra vì không có lỗi hay cảnh báo nào.
3. **`target:` không miễn nhiễm với cache ở tầng khác** — nó chỉ quyết định build gì, không quyết định có build hay không; một thứ tưởng chừng không liên quan (tên image trùng) vẫn có thể vô hiệu hoá nó hoàn toàn.
4. **`.env.example` không tự nhiên có tác dụng** — phải thực sự có `${VAR}` trong file cấu hình tham chiếu tới nó; nếu không, nó chỉ là tài liệu, không phải cấu hình.
5. **Không phải biến nào cũng nên cho ghi đè** — chỉ mở `${VAR}` cho những thứ thực sự khác nhau giữa các lần triển khai; giữ cứng những gì định nghĩa bản chất của file (production vs dev).
