## 📚 Lý thuyết: Information Disclosure là gì?

### Vấn đề

Nhiều website vô tình **để lộ** file cấu hình, source code, hoặc thông tin hệ thống mà ai cũng truy cập được. Hacker chỉ cần gõ URL:

```
https://example.com/.env          → Lộ mật khẩu database!
https://example.com/.git/HEAD     → Clone toàn bộ source code!
https://example.com/robots.txt    → Biết admin panel ở đâu!
```

Đây là lỗi **Information Disclosure** — thuộc nhóm *Security Misconfiguration* (OWASP Top 10:2021, mục A05).

---

## 📚 Các file nhạy cảm thường gặp

### 1. `/.env` — Severity: CRITICAL

File `.env` chứa **biến môi trường** — nơi developer lưu mật khẩu, API keys:

```env
DATABASE_URL=postgresql://admin:SuperSecret123@db.example.com/prod
JWT_SECRET=my-super-secret-key-never-share
AWS_ACCESS_KEY_ID=AKIA1234567890
```

→ Nếu lộ ra, hacker truy cập được database, cloud, mọi thứ!

**Nguyên nhân:** Developer quên chặn file `.env` trong cấu hình web server (Nginx/Apache).

---

### 2. `/.git/HEAD` — Severity: CRITICAL

Nếu file `/.git/HEAD` trả về `200 OK` → thư mục `.git` bị lộ → hacker có thể **clone toàn bộ source code**:

```bash
# Hacker dùng tool như git-dumper:
git-dumper https://example.com/.git/ ./source_code
# → Có toàn bộ code, commit history, secret keys trong code cũ!
```

**Nguyên nhân:** Deploy bằng `git pull` trên server mà không chặn thư mục `.git`.

---

### 3. `/robots.txt` — Severity: LOW

`robots.txt` hướng dẫn bot (Google, Bing) nên/không nên crawl gì:

```
User-agent: *
Disallow: /admin/
Disallow: /api/internal/
Disallow: /backup/
```

→ Hacker đọc `Disallow` = biết ngay **đường dẫn ẩn** mà admin muốn giấu!

**Lưu ý:** `robots.txt` tồn tại không phải lúc nào cũng xấu — nó là file chuẩn. Nhưng cần kiểm tra nội dung có lộ đường dẫn nhạy cảm không.

---

### 4. Server Header — Severity: MEDIUM

Response header `Server` tiết lộ **phần mềm và phiên bản** web server:

```
Server: Apache/2.4.41 (Ubuntu)
Server: nginx/1.18.0
```

→ Hacker biết version → tìm **CVE** (lỗ hổng đã công bố) → tấn công!

```
Apache 2.4.41 → CVE-2020-1927 (Open Redirect)
nginx 1.18.0  → CVE-2021-23017 (DNS Resolver)
```

---

### 5. X-Powered-By Header — Severity: MEDIUM

Header `X-Powered-By` tiết lộ **framework/ngôn ngữ**:

```
X-Powered-By: Express        → Node.js Express
X-Powered-By: PHP/7.4.3      → PHP version
X-Powered-By: ASP.NET        → .NET framework
```

→ Cùng nguyên lý: biết công nghệ → tìm lỗ hổng → tấn công!

---

### 6. `/wp-admin` — Severity: MEDIUM

Đường dẫn mặc định của **trang quản trị WordPress**:

```
https://example.com/wp-admin   → Trang đăng nhập admin!
https://example.com/wp-login.php
```

→ Nếu trả về `200 OK` → Hacker biết website dùng WordPress → tập trung tấn công:
- Brute-force mật khẩu admin
- Exploit plugin/theme lỗi thời
- Dùng WPScan quét toàn bộ lỗ hổng WordPress

**Lưu ý:** Check này chỉ có ý nghĩa với site WordPress. Với site khác sẽ trả về 404 → không có finding.

---

## 📚 Khác biệt kiến trúc với module trước

### HeadersModule: 1 request → nhiều checks

```
GET https://example.com → Response
  ├── Check header CSP?       → Thiếu → Finding
  ├── Check header HSTS?      → Thiếu → Finding
  └── Check header X-Frame?   → Có    → OK
```

### InformationModule: Nhiều requests → mỗi request 1 check

```
GET https://example.com/.env       → 404 → OK
GET https://example.com/.git/HEAD  → 404 → OK
GET https://example.com/robots.txt → 200 → Finding!
GET https://example.com            → Check Server header → Finding!
```

→ Module này gửi **nhiều HTTP requests** nên sẽ chậm hơn.

---

## 💻 Code hoàn chỉnh

File: `backend/app/modules/information.py`

```python
import httpx
from app.modules.base import HTTP_TIMEOUT, BaseModule

class InformationModule(BaseModule):
    @property
    def name(self) -> str:
        return "information"

    @property
    def description(self) -> str:
        return "Rà soát lộ file và thông tin nhạy cảm"

    SENSITIVE_PATHS = [
        {
            "path": "/.env",
            "severity": "critical",
            "description": "File .env chứa biến môi trường nhạy cảm",
            "remediation": "Chặn truy cập file .env trong web server"
        },
        {
            "path": "/.git/HEAD",
            "severity": "critical",
            "description": "Lộ thông tin về git repository",
            "remediation": "Chặn truy cập thư mục .git"
        },
        {
            "path": "/robots.txt",
            "severity": "low",
            "description": "File robots.txt có thể lộ đường dẫn ẩn",
            "remediation": "Kiểm tra robots.txt không chứa path nhạy cảm"
        },
        {
            "path": "/wp-admin",
            # /wp-admin thường trả 301/302 chuyển tới wp-login.php thay vì 200
            "redirect_markers": ("wp-login.php", "/wp-admin/"),
            "severity": "medium",
            "description": "Cổng quản trị website",
            "remediation": "Tăng cường bảo mật cho cổng quản trị"
        }
    ]
REDIRECT_STATUSES = (301, 302, 303, 307, 308)

    async def scan(self, url: str, **kwargs) -> list:
        findings = []
        async with httpx.AsyncClient(timeout=HTTP_TIMEOUT) as client:
            # Check từng sensitive path
            for item in self.SENSITIVE_PATHS:
                target = url.rstrip("/") + item["path"]
                try:
                    response = await client.get(target)
                    exposed = response.status_code == 200
                    if not exposed and "redirect_markers" in item:
                        # Không theo redirect (tránh SSRF) nên tự đọc header Location
                        location = response.headers.get("location", "").lower()
                        exposed = (response.status_code in REDIRECT_STATUSES
                                   and any(m in location for m in item["redirect_markers"]))
                    if exposed:
                        findings.append({...})
                except httpx.HTTPError:
                    pass   # lỗi mạng/timeout của 1 path không ảnh hưởng path khác

            # Check Server + X-Powered-By headers
            try:
                response = await client.get(url)
                server = response.headers.get("Server")
                if server:
                    findings.append({...})

                xpb = response.headers.get("X-Powered-By")
                if xpb:
                    findings.append({...})
            except httpx.HTTPError:
                pass

        return findings
```

### Lưu ý thiết kế:

| Quyết định | Lý do |
|------------|-------|
| Path checks và Header checks tách riêng | Path cần nhiều requests, Header chỉ cần 1 |
| `X-Powered-By` không nằm trong `SENSITIVE_PATHS` | Vì nó là header, không phải đường dẫn file |
| Dùng `try/except httpx.HTTPError` bọc mỗi request | 1 path lỗi không ảnh hưởng các path khác |
| Bắt **`httpx.HTTPError`** thay vì `except:` trần | `except:` trần nuốt cả `KeyboardInterrupt`, `asyncio.CancelledError` (làm hỏng việc **hủy scan**) và mọi lỗi lập trình. Chỉ nên bắt đúng loại lỗi mình chủ đích bỏ qua |

## ⚠️ Giới hạn đã biết

| Vấn đề | Giải thích |
|---|---|
| ~~Chỉ coi `200 OK` là "lộ"~~ → **đã xử lý cho `/wp-admin`** | WordPress thật thường trả **301/302** chuyển `/wp-admin` tới `wp-login.php` (hoặc `/wp-admin/`). `httpx` **không theo redirect** (chủ ý, tránh SSRF), nên module **tự đọc header `Location`**: nếu status là 301/302/303/307/308 *và* `Location` chứa `wp-login.php` hoặc `/wp-admin/` thì coi là phát hiện. Luật redirect chỉ áp dụng cho `/wp-admin` (khai báo bằng `redirect_markers`), không áp dụng cho `/.env`, `/.git/HEAD`. Site chuyển *mọi* đường dẫn lạ về trang chủ (`Location: /`) **không** bị báo nhầm |
| Soft-404 → dương tính giả | Một số site (SPA, trang lỗi tùy biến) trả `200` cho **mọi** đường dẫn, kể cả `/.env` → báo `critical` sai. Cách chặt hơn là kiểm tra nội dung (vd `/.git/HEAD` phải bắt đầu bằng `ref:`) |
| `/robots.txt` luôn bị báo `low` nếu tồn tại | Dù file chuẩn là hợp lệ; code **không** đọc nội dung `Disallow` như phần lý thuyết gợi ý |
| Không theo redirect là chủ ý | Theo redirect sẽ mở lối cho SSRF (site công khai chuyển hướng tới `http://127.0.0.1/...`) — nên mặc định tắt là an toàn |

## 🔑 Takeaway

1. **Information Disclosure** = lộ file cấu hình, source code, thông tin hệ thống
2. **`.env` và `.git`** = critical — lộ mật khẩu và source code
3. **Server/X-Powered-By headers** = lộ version → hacker tìm CVE
4. **Nhiều requests** = duyệt từng path, bọc try/except riêng
5. **Tách logic**: path checks vs header checks — không trộn lẫn

## 📚 Cập nhật sau Sprint 1 — từ 4 lên 37 kiểm tra, vá lỗi soft-404

> Đây là module thay đổi nhiều nhất: 4 đường dẫn ban đầu (`.env`, `.git/HEAD`, `robots.txt`, `wp-admin`) lên **33 đường dẫn mới** + 4 kiểu kiểm tra hoàn toàn mới (directory listing, lỗi chi tiết, IP nội bộ, header phiên bản). Nhưng thay đổi **quan trọng nhất về chất lượng** không phải số lượng — mà là vá đúng lỗi "Soft-404" đã tự dự đoán trước.

### 1. Vá lỗi Soft-404 bằng "chữ ký nội dung" (signature)

**Vấn đề cũ:** chỉ cần `status_code == 200` là coi như "lộ file". Một SPA (React/Vue) thường cấu hình server trả **cùng một trang `index.html`** cho *mọi* URL không khớp route (để client-side router tự xử lý) — tức là `/.env`, `/.aws/credentials`, `/id_rsa`... đều trả `200` với **nội dung y hệt trang chủ**. Module cũ sẽ báo hàng chục `critical` sai hoàn toàn trên một site không hề lộ gì.

**Cách vá:** mỗi mục trong `SENSITIVE_PATHS` có thể khai báo thêm `"signature"` — một regex (dạng *bytes*) mô tả **nội dung thật** của đúng loại file đó phải có:
```python
{
    "path": "/.git/config",
    "signature": rb"\[core\]",
    "severity": "critical",
    ...
},
{
    "path": "/backup.sql",
    "signature": rb"CREATE TABLE|INSERT INTO|DROP TABLE|MySQL dump|PostgreSQL database dump",
    ...
},
```
Khi path có `signature`, "lộ" không còn là `status == 200` nữa, mà là:
```python
exposed = response.status_code in EXPOSED_STATUSES   # (200, 206)
if exposed and signature:
    exposed = re.search(signature, body) is not None
```
4 path gốc (`.env`, `.git/HEAD`, `robots.txt`, `wp-admin`) **không có** signature — giữ nguyên hành vi cũ (chỉ cần 200), vì nội dung `.env` quá đa dạng để viết một regex chung đáng tin cậy.

### 2. Tự phát hiện site "trả 200 cho mọi thứ" (catch-all) trước khi quét

Signature xử lý được trường hợp *nội dung sai*, nhưng vẫn cần một lớp phòng thủ nữa: nếu site là catch-all, **toàn bộ 33 path không-có-signature mới** (phần lớn file nhị phân/khó viết regex, ví dụ `.DS_Store`) vẫn có nguy cơ báo sai. Giải pháp: quét thử **một đường dẫn chắc chắn không tồn tại** trước, dùng UUID ngẫu nhiên để không ai đoán trước được:
```python
probe = f"{url.rstrip('/')}/webguard-{uuid.uuid4().hex[:12]}?id=%27%22%5C"
baseline = await self._get(client, probe, gate)
catch_all = baseline is not None and baseline.status_code == 200
```
Nếu `catch_all == True`, mọi path **không có signature** bị bỏ qua hoàn toàn (không đáng tin cậy để kiểm tra bằng status code nữa):
```python
if catch_all and not signature:
    return None
```
→ Đây là lý do `/.env` (không signature) sẽ **không** được báo trên một SPA catch-all, nhưng `/.git/config` (có signature) **vẫn** được báo nếu nội dung thật sự khớp `[core]` — thử nghiệm trong `test_catch_all_site_still_reports_a_real_leak`.

> 💡 Query string `?id=%27%22%5C` (dấu `'`, `"`, `\` đã encode) trong cùng request dò catch-all được tái sử dụng luôn cho mục 4 (lỗi chi tiết) — "tiện thể" kiểm tra server có in lỗi khi gặp input lạ không, không cần thêm request riêng.

### 3. `Range` header — không tải cả file backup nặng

Nhiều path mới là backup/dump (`backup.sql`, `backup.zip`...) có thể **rất nặng**. Quét chỉ cần vài KB đầu để khớp signature, không cần tải hết:
```python
MAX_BODY_BYTES = 65536  # 64KB
return await client.get(target, headers={"Range": f"bytes=0-{MAX_BODY_BYTES - 1}"})
```
Server hỗ trợ `Range` sẽ trả `206 Partial Content` kèm đúng phần đầu file — đủ để regex signature khớp. Server không hỗ trợ `Range` (phần lớn static file server vẫn hỗ trợ) thì trả nguyên `200` — code vẫn hoạt động, chỉ là tải nhiều hơn cần thiết.

### 4. Chạy song song bằng `asyncio.gather` + giới hạn đồng thời

37 path quét tuần tự (như code gốc) sẽ rất chậm. Nhưng quét **quá nhiều request cùng lúc** vào 1 site cũng không nên (giống một kiểu DoS nhẹ ngoài ý muốn). Cân bằng bằng `asyncio.Semaphore`:
```python
gate = asyncio.Semaphore(MAX_CONCURRENCY)  # tối đa 8 request đồng thời

async def _get(self, client, target, gate):
    async with gate:   # chờ nếu đã có 8 request khác đang chạy
        return await client.get(target, headers=...)

results = await asyncio.gather(
    *[self._check_path(client, url, item, catch_all, gate) for item in self.SENSITIVE_PATHS],
    *[self._check_directory(client, url, path, gate) for path in DIRECTORY_PATHS],
)
```
`asyncio.Semaphore` hoạt động như "vé vào cửa": có `MAX_CONCURRENCY` vé, hết vé thì task mới phải `await` đến khi có task khác trả vé (ra khỏi khối `async with gate`).

### 5. Ba kiểu kiểm tra mới không phải "path" theo nghĩa cũ

- **`directory_listing`** (medium): thử các thư mục hay bật "liệt kê file" (`/uploads/`, `/backup/`, cả trang chủ `/`), tìm dấu hiệu `<title>Index of /` trong HTML — Apache/Nginx đều dùng cụm này khi `Options +Indexes` (Apache) hoặc `autoindex on` (Nginx) đang bật.
- **`verbose_error_messages`** (medium): dùng lại chính request dò catch-all (mục 2) — ký tự lạ trong query (`'`, `"`, `\`) thường khiến code xử lý kém an toàn ném lỗi chưa bắt (stack trace Python, lỗi cú pháp SQL...). Regex `ERROR_SIGNATURES` gom nhiều "chữ ký lỗi" của Python/PHP/Java/.NET/SQL:
  ```python
  rb"Traceback \(most recent call last\)"
  rb"|You have an error in your SQL syntax"
  rb"|ORA-\d{5}"              # Oracle
  rb"|SQLSTATE\["             # nhiều driver PHP
  ```
- **`internal_ip_disclosure`** (low): regex tìm IP dải private (`10.x`, `172.16-31.x`, `192.168.x`) ngay trong HTML trả về — thường lộ qua comment debug hoặc URL API nội bộ hard-code nhầm ra frontend.

### 6. Kết quả kiểm chứng (test mới)

`tests/unit/test_information_extended.py` (32 test) — ví dụ xác nhận catch-all không gây dương tính giả nhưng vẫn bắt được lỗi thật:
```python
async def test_catch_all_site_does_not_flood_with_false_positives() -> None:
    spa = _resp(200, "<html><div id='root'></div></html>")
    assert await _scan({}, default=spa) == []   # không có path nào có signature khớp

async def test_catch_all_site_still_reports_a_real_leak() -> None:
    spa = _resp(200, "<html><div id='root'></div></html>")
    findings = await _scan({"/.git/config": _resp(200, "[core]\nbare = false")}, default=spa)
    assert _names(findings) == ["/.git/config"]   # có signature -> vẫn bắt được
```

### 🔑 Takeaway (bổ sung)

1. **Một kiểm tra chỉ dựa vào status code luôn mong manh** trước site catch-all/SPA — cần thêm "chữ ký nội dung" khi có thể, và một bước tự phát hiện catch-all cho những path không viết được chữ ký đáng tin.
2. **Giới hạn độ dài tải về (`Range`)** khi mục tiêu là *phát hiện sự tồn tại* của file, không phải *tải* file.
3. **`asyncio.Semaphore`** = cách đơn giản để "chạy song song nhưng có giới hạn" — nhanh hơn tuần tự, lịch sự hơn "không giới hạn gì cả".
4. **Giới hạn tự ghi lại trong tài liệu** (mục "Giới hạn đã biết") là một dạng backlog miễn phí — quay lại đọc để biết nên làm gì tiếp theo.
