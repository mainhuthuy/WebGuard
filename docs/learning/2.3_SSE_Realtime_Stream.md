## 🧭 1. Tại sao dùng SSE (Server-Sent Events) thay vì WebSocket hay Polling?

### Vấn đề của Polling truyền thống
- Client gửi request hỏi liên tục: *"Quét xong chưa?"*, *"Quét xong chưa?"* mỗi giây 1 lần.
- **Hậu quả:** Máy chủ bị quá tải vì phải xử lý hàng trăm request thừa, tốn băng thông và gây trễ (delay).

### So sánh SSE vs WebSocket
| Tiêu chí | SSE (Server-Sent Events) | WebSocket |
|---|---|---|
| **Hướng truyền tin** | **1 chiều:** Server ➔ Client | **2 chiều:** Client ⇄ Server |
| **Giao thức** | Chuẩn HTTP (`text/event-stream`) | Giao thức riêng biệt (`ws://`, `wss://`) |
| **Bảo mật & Tường lửa** | Đi qua Firewall/Proxy doanh nghiệp cực dễ | Dễ bị Firewall/Proxy chặn |
| **Tự động kết nối lại** | Trình duyệt tự động Reconnect khi mất mạng (⚠️ xem lưu ý bên dưới) | Phải tự viết logic reconnect thủ công |
| **Tính phù hợp** | **Hoàn hảo cho Dashboard quét bảo mật, tin tức, log** | **Game thời gian thực, Chat app 2 chiều** |

👉 Người dùng trên WebGuard chỉ cần **ngồi xem kết quả quét chạy về**, không cần gửi ngược lại gì cả. Do đó **SSE là lựa chọn tối ưu, nhẹ và an toàn nhất**.

> ⚠️ **"Tự động reconnect" là con dao hai lưỡi với WebGuard.** `EventSource` tự mở lại kết nối khi bị đứt. Nhưng endpoint `GET /scan/{id}/stream` của ta **vừa là luồng xem vừa là thứ kích hoạt việc quét**: nếu kết nối lại giữa lúc scan còn đang chạy, server sẽ khởi động một lượt quét thứ hai cho cùng `scan_id`. Cơ chế *replay* (mục 4) chỉ bảo vệ khi scan đã `COMPLETED`. Vì vậy frontend (`hooks/useSSE.ts`) **đóng `EventSource` ngay khi có lỗi** thay vì để nó tự nối lại, và hiển thị lỗi cho người dùng.

## 📚 2. Khái niệm Kỹ thuật: Python Async Generator (`yield`)

Thông thường hàm trong Python dùng `return` để trả về kết quả 1 lần duy nhất rồi kết thúc:
```python
def scan_tat_ca():
    # Phải quét xong hết cả 5 module rồi mới trả về
    return ["Headers OK", "Cookies OK", "SSL OK"]
```

Nhưng với **Async Generator (`yield`)**:
```python
async def scan_stream():
    yield "1. Bắt đầu quét..."
    await quet_headers()
    yield "2. Headers xong! (Tìm thấy 2 lỗi)"
    await quet_ssl()
    yield "3. SSL xong! (Hạn 90 ngày)"
```
Mỗi khi một module chạy xong, hàm sẽ **tạm dừng và "bắn" ngay gói tin đó ra ngoài (`yield`)**, giúp Frontend nhận được dữ liệu ngay lập tức mà không phải chờ các module khác.

## 🛠️ 3. Cấu trúc Gói tin Sự kiện (Event Schema)

File: [`backend/app/schemas/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/schemas/scan.py)

Mỗi sự kiện bắn qua SSE đều tuân theo format:
```json
{
  "event": "module_completed",
  "scan_id": "b3e945c1-84fb-4b3f-b258-009c91f64f40",
  "progress": 40,
  "message": "Hoàn thành cookies (phát hiện 1 vấn đề)",
  "module": "cookies",
  "findings": [
    {
      "module": "cookies",
      "name": "session_id",
      "flag_missing": "HttpOnly",
      "severity": "high",
      "description": "Ngăn cookie bị đánh cắp bởi XSS",
      "remediation": "Thêm cookie flag: HttpOnly",
      "url": "https://example.com"
    }
  ],
  "data": { "count": 1 }
}
```

### Các trạng thái sự kiện (`ScanEventType`):
- `START` (5%): Khởi tạo phiên quét mục tiêu (`data.total_modules` = 5 hoặc 2 tùy `mode`).
- `MODULE_START` (10% → 70% với 5 module): Module bảo mật chuẩn bị chạy.
- `MODULE_COMPLETED` (25% → **85%** với 5 module): Module hoàn tất kèm danh sách lỗ hổng mới phát hiện.
- Công thức: `start = 10 + (i−1)·75/N`, `completed = 10 + i·75/N` (N = số module, xem 1.8).
- `SCORING` (95%): Tính điểm an ninh (A+, A, B, C, F).
- `COMPLETE` (100%): Toàn bộ quá trình quét kết thúc thành công.
- `ERROR`: Quá trình gặp sự cố ngoài dự kiến.

## 💻 4. Triển khai API SSE với `sse-starlette`

File: [`backend/app/api/v1/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/api/v1/scan.py)

```python
@router.get("/{scan_id}/stream", response_class=EventSourceResponse)
async def stream_scan_progress(scan_id: str, db: Session = Depends(get_db)) -> EventSourceResponse:
    # 1. Kiểm tra scan_id có tồn tại không (DB trước, bộ nhớ đệm sau)
    scan = scan_service.get_scan(db, scan_id)
    if not scan and scan_id not in scan_jobs:
        raise ScanNotFoundException(scan_id=scan_id)

    async def event_generator():
        # 2. ScanService.stream_scan lo toàn bộ logic nghiệp vụ:
        #    - scan đã COMPLETED  -> chỉ phát lại sự kiện `complete` (replay)
        #    - ngược lại          -> đặt RUNNING, chạy Scanner(mode=scan.mode).scan_stream(...),
        #                            khi `complete` thì lưu findings + điểm vào DB
        async for step_event in scan_service.stream_scan(scan_id=scan_id, db=db):
            yield ServerSentEvent(
                event=step_event["event"],
                data=json.dumps(step_event, default=str, ensure_ascii=False),
            )

    return EventSourceResponse(event_generator())
```

> 📌 Phiên bản ở task 2.3 gốc chỉ dùng dict `scan_jobs` trong RAM. Hiện giờ router chỉ còn nhiệm vụ HTTP/SSE; **logic quét + lưu DB nằm trong `ScanService.stream_scan`** (xem 2.9). Sự kiện `error` được phát khi scanner ném ngoại lệ ngoài dự kiến.

## 🔑 Tóm tắt cốt lõi (Takeaway)

1. **SSE là chuẩn tốt nhất cho Dashboard Quét:** Nhẹ hơn WebSocket, vượt tường lửa dễ dàng, tự động reconnect.
2. **Async Generator (`yield`):** Giúp hàm phát dữ liệu ra ngoài từng bước thay vì bắt client chờ hoàn thành tất cả.
3. **Format chuẩn HTML5 SSE:** Gồm `event: <tên_sự_kiện>` và `data: <chuỗi_json_utf8>`.
4. **Cơ chế Replay:** Giữ trạng thái `COMPLETED` để người dùng F5 hoặc mở lại tab không bị quét trùng lặp gây lãng phí tài nguyên. *Chỉ áp dụng cho scan đã xong* — mở lại luồng của scan đang chạy sẽ chạy lại scan.
5. **Tên sự kiện (`event:`):** server gửi *named events*, nên client phải dùng `addEventListener('module_completed', ...)` cho từng loại; `onmessage` chỉ nhận sự kiện không đặt tên.
