# Task 4.5 — CI: Frontend Pipeline (ESLint + TSC + Build check)

> **Mục tiêu:** Mỗi PR đụng vào `frontend/**` tự động chạy 3 kiểm tra: **ESLint** (chất lượng code), **TSC** (kiểu dữ liệu), **Vite build** (bundle dựng được). Thiếu một trong ba thì lỗi vẫn có thể lọt vào `main`.
>
> File triển khai: `.github/workflows/frontend-ci.yml` (cùng khuôn với `backend-ci.yml` ở task 4.4)

---

## 📚 Lý thuyết: vì sao cần cả 3, không bù trừ được cho nhau

| Kiểm tra | Bắt được | Không bắt được |
|---|---|---|
| **ESLint** | Hook dùng sai (`react-hooks`), biến thừa, pattern dễ gây bug | Sai kiểu dữ liệu |
| **TSC** (`tsc -b`) | Gọi hàm sai tham số, thiếu field, `undefined` chưa xử lý | Bug logic/hook, lỗi bundler |
| **Vite build** | Import sai đường dẫn, module không resolve được, lỗi bundle/tree-shaking | Lỗi kiểu (Vite chỉ *xoá* type, không kiểm tra) |

> 🔑 Điểm hay bị hiểu nhầm: **Vite/esbuild không type-check.** Nó chỉ gỡ type annotation rồi đóng gói. Code sai kiểu vẫn build thành công. Đó là lý do `package.json` viết `"build": "tsc -b && vite build"` — kiểm tra kiểu là bước **riêng**, không tự có.

### `tsc -b` là gì?
`-b` = **build mode**, đi theo các *project references* trong `tsconfig.json`:
```json
{ "files": [], "references": [
    { "path": "./tsconfig.app.json" },   // src/  (React, DOM)
    { "path": "./tsconfig.node.json" }   // vite.config.ts (Node)
] }
```
Hai môi trường khác nhau (trình duyệt vs Node) nên cần hai config riêng. Gõ `tsc --noEmit` thẳng ở gốc sẽ **không kiểm tra gì** vì `files: []` — phải dùng `-b`. Cả hai config đã có `noEmit: true` nên chỉ kiểm tra, không sinh file.

### `npm ci` và `npm install`
`npm ci` cài **đúng** theo `package-lock.json`, xoá `node_modules` trước, và **báo lỗi** nếu lock lệch `package.json`. Trên CI ta muốn tái lập được, không muốn tự nâng phiên bản ngầm — nên luôn dùng `npm ci`.

## 🛠 Thiết kế workflow & lý do

Giữ nguyên các quyết định của 4.4: trigger lọc `paths: frontend/**`, `concurrency` huỷ lần chạy cũ, `defaults.run.working-directory`. Phần khác biệt:

### 1. Ba job song song: `lint`, `typecheck`, `build`
Mỗi job báo đúng một loại lỗi, trên PR thấy ngay cái nào đỏ. Đánh đổi: `npm ci` chạy 3 lần — giảm nhẹ bằng cache npm.

### 2. Cache npm theo `package-lock.json`
```yaml
- uses: actions/setup-node@v4
  with:
    node-version: "22"
    cache: "npm"
    cache-dependency-path: frontend/package-lock.json
```
`cache-dependency-path` bắt buộc ghi đủ `frontend/...` vì lockfile không nằm ở gốc repo (và `working-directory` không áp dụng cho `uses:`).

Node **22** khớp với `node:22-alpine` trong Dockerfile (task 4.2) → CI và image production dùng cùng major version.

### 3. Job build gọi `npx vite build`, không gọi `npm run build`
`npm run build` = `tsc -b && vite build` — sẽ chạy lại type-check lần nữa, trùng với job `typecheck`. Tách ra thì lỗi kiểu báo ở đúng job, job build chỉ trả lời "bundle có dựng được không".

> Đánh đổi: nếu ai đó đổi script `build` trong `package.json` (vd thêm bước), CI không tự theo. Chấp nhận vì đổi lại báo lỗi rõ ràng hơn.

## ✅ Kiểm chứng (chạy đúng các lệnh CI trên máy local)

```bash
cd frontend
npm ci
npm run lint        # sạch, không cảnh báo
npx tsc -b          # sạch
npx vite build      # ✓ built in ~9s
```
Cả ba đều xanh trên code hiện tại.

Cách tái hiện: chạy 4 `vitest run` song song để giả lập máy bận → 2 test đỏ: `AboutPage > lists every module...` (hết 5s timeout mặc định) và `App > goes through to the results page...` (`findByText('A+')` hết `asyncUtilTimeout` 5s vì chunk lazy của trang kết quả tải chậm). Sửa: `testTimeout: 20000` ở `vite.config.ts` và `asyncUtilTimeout: 15000` ở `src/test/setup.ts` (giữ nhỏ hơn testTimeout để lỗi hiện rõ "Unable to find..."). Sau đó 4 lần chạy song song đều 137/137.

## 🔑 Bài học
1. **Type-check và build là hai việc khác nhau** trong hệ sinh thái Vite.
2. **`tsc -b` + project references**: dùng `-b`, không dùng `--noEmit` ở gốc.
3. **`npm ci` trên CI** để build tái lập được.
4. **Test chập chờn phải xử lý trước khi cho vào CI** — CI mất giá trị nếu nó đỏ ngẫu nhiên.
