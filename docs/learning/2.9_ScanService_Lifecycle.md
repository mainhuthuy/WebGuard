# Task 2.9 — Quản Lý Vòng Đời Phiên Quét Với `ScanService` (Lifecycle Management)

> **Mục tiêu:** Xây dựng tầng dịch vụ `ScanService` (Service Layer Pattern) đóng gói toàn bộ quy tắc nghiệp vụ quản lý vòng đời một phiên quét an ninh: khởi tạo, lưu trữ DB, thực thi song song, quản lý background task, hỗ trợ hủy (cancel) và phát stream thời gian thực.

---

## 📚 1. Lý thuyết nền tảng

### 1.1 Service Layer Pattern là gì? Tại sao cần tách khỏi API Router?

Trong kiến trúc ứng dụng web hiện đại (Clean Architecture / Layered Architecture):
* **API Routers (Controllers)** chỉ nên làm nhiệm vụ: tiếp nhận HTTP Request, validate schema (Pydantic), gọi Service xử lý và trả về HTTP Response.
* **Service Layer (`ScanService`)** là nơi chứa toàn bộ **Business Logic** (luật nghiệp vụ): điều phối database, gọi scanner engine, kiểm soát tiến trình, tính toán logic và xử lý ngoại lệ.

```
┌──────────────────────────────────────────────┐
│            FastAPI Routers (Endpoints)       │  <-- Chỉ xử lý HTTP / Status codes
└──────────────────────┬───────────────────────┘
                       │ Calls
┌──────────────────────▼───────────────────────┐
│        ScanService (Service Layer)           │  <-- Điều phối toàn bộ vòng đời Scan
└───────┬──────────────────────────────┬───────┘
        │ Queries / Updates            │ Orchestrates
┌───────▼───────────────┐      ┌───────▼───────────────┐
│  Database (SQLAlchemy)│      │  Scanner Orchestrator │
└───────────────────────┘      └───────────────────────┘
```

**Lợi ích:**
1. **Separation of Concerns (Phân tách trách nhiệm)**: Router không bị phình to (Fat Controller anti-pattern).
2. **Reusability (Tái sử dụng)**: Logic quét có thể được gọi từ HTTP Endpoint, Background Worker, CLI script hoặc Cron Job mà không cần giả lập HTTP Request.
3. **Testability (Dễ viết Unit Test)**: Có thể test trực tiếp Service method với DB in-memory mà không cần dựng full Web Server qua TestClient.

### 1.2 Máy trạng thái vòng đời phiên quét (Scan Lifecycle State Machine)

Một phiên quét bảo mật trong WebGuard trải qua các trạng thái tuần tự và hữu hạn:

```
                  ┌───────────────┐
                  │    PENDING    │ (Đã tạo trong DB, chờ khởi động)
                  └───────┬───────┘
                          │ execute / stream
                          ▼
                  ┌───────────────┐
     ┌───────────►│    RUNNING    ├───────────┐
     │            └───────┬───────┘           │
     │ Cancelled          │ Done              │ Error / Timeout
     ▼                    ▼                   ▼
┌───────────┐     ┌───────────────┐     ┌───────────┐
│ CANCELLED │     │   COMPLETED   │     │  FAILED   │
└───────────┘     └───────────────┘     └───────────┘
 (Bị hủy bỏ)      (Lưu điểm, findings)   (Lưu lỗi)
```

| Trạng thái | Mô tả | Chuyển dịch kế tiếp |
|------------|-------|---------------------|
| `pending` | Vừa tạo ID và bản ghi trong DB, chưa chạy các module quét | `running`, `cancelled` |
| `running` | Các module quét (Headers, Cookies, SSL...) đang gửi request | `completed`, `failed`, `cancelled` |
| `completed` | Quét xong toàn bộ module của `mode` đã chọn (7 cho `full`, 2 cho `quick` — xem `1.8`), đã tính điểm an toàn và lưu findings vào DB | Trạng thái kết thúc (Terminal) |
| `failed` | Gặp lỗi mạng hoặc crash ngoại lệ ngoài dự kiến | Trạng thái kết thúc (Terminal) |
| `cancelled` | Người dùng chủ động gửi yêu cầu dừng quét | Trạng thái kết thúc (Terminal) |

### 1.3 Quản lý Background Task & Huỷ tác vụ (`asyncio.Task`)

Khi người dùng không muốn giữ kết nối stream mà muốn hệ thống chạy ngầm:
1. `asyncio.create_task(...)`: Lập lịch cho một coroutine chạy ngầm trên Event Loop của Python.
2. Quản lý tác vụ qua Registry: `_active_tasks: dict[str, asyncio.Task[Any]]` lưu trữ mapping giữa `scan_id` và đối tượng `Task`.
3. Huỷ tác vụ bằng `task.cancel()`:
   * Khi gọi `cancel()`, Python sẽ ném ngoại lệ `asyncio.CancelledError` vào điểm `await` tiếp theo của coroutine.
   * `ScanService` bắt `CancelledError`, cập nhật trạng thái `cancelled` vào DB và dọn dẹp tài nguyên.
4. Tự động dọn dẹp: Dùng `task.add_done_callback(...)` để xóa `scan_id` khỏi `_active_tasks` ngay khi coroutine kết thúc (dù thành công, thất bại hay bị hủy).

---

### 1.4 Lưu ý kiến trúc: Quản lý Database Session trong Background Task

> ⚠️ **CẠM BẪY PHỔ BIẾN TRONG FASTAPI + SQLALCHEMY:**
> * `get_db()` là một request-scoped dependency. Khi HTTP response trả về xong, session `db` sẽ **tự động bị đóng (`db.close()`)**.
> * Nếu một background task chạy ngầm sau khi response đã trả về mà vẫn cố dùng lại `db` session cũ → **lỗi `StatementError: Database is closed` hoặc rò rỉ dữ liệu**.
> * **Giải pháp chuẩn:** Trong `execute_scan`, nếu không nhận session từ ngoài, Service sẽ tự tạo session độc lập qua `SessionLocal()` và đảm bảo đóng trong khối `try...finally`.

## 💻 2. Chi tiết triển khai code

### 2.1 File: `backend/app/services/scan.py`

```python
class ScanService:
    def __init__(self) -> None:
        self._active_tasks: dict[str, asyncio.Task[Any]] = {}

    def create_scan(self, db: Session, target_url: str, mode: str = "full") -> ScanModel:
        """Tạo bản ghi mới trong DB với status=pending (và chế độ quét quick/full)."""
        scan_id = str(uuid.uuid4())
        scan_record = ScanModel(
            id=scan_id,
            target_url=target_url,
            mode=mode,
            status=ScanStatus.PENDING.value,
            created_at=datetime.now(timezone.utc),
        )
        db.add(scan_record)
        db.commit()
        db.refresh(scan_record)
        return scan_record

    def cancel_scan(self, db: Session, scan_id: str) -> bool:
        """Hủy phiên quét: cancel asyncio task và đổi status thành cancelled."""
        scan = self.get_scan(db, scan_id)
        if not scan or scan.status in (ScanStatus.COMPLETED.value, ScanStatus.FAILED.value, ScanStatus.CANCELLED.value):
            return False

        task = self._active_tasks.get(scan_id)
        if task and not task.done():
            task.cancel()

        scan.status = ScanStatus.CANCELLED.value
        scan.completed_at = datetime.now(timezone.utc)
        db.commit()
        db.refresh(scan)
        return True
```

### 2.1b Hai đường thực thi: `execute_scan` và `stream_scan`

| | `execute_scan` / `start_background_scan` | `stream_scan` |
|---|---|---|
| Kích hoạt | Gọi từ code (chạy nền bằng `asyncio.create_task`) | Khi client mở `GET /scan/{id}/stream` |
| Engine | `Scanner(mode).scan()` — **song song** | `Scanner(mode).scan_stream()` — **tuần tự**, phát sự kiện |
| DB session | Tự tạo `SessionLocal()` rồi đóng | Dùng session của request (`Depends(get_db)`) |
| Giao diện web dùng | Không | **Có** — đây là đường người dùng đi qua |

Cả hai đều lưu findings + điểm vào DB khi xong và đều đăng ký task vào `_active_tasks` để có thể hủy. Hiện endpoint HTTP **chưa** gọi `start_background_scan` — nó có sẵn trong service để dùng cho CLI/cron hoặc chế độ quét nền sau này.

### 2.2 Replay Mechanism trong SSE Stream

Khi client bị ngắt mạng và kết nối lại endpoint `GET /api/v1/scan/{id}/stream`:
* `ScanService.stream_scan` kiểm tra xem phiên quét trong DB đã ở trạng thái `COMPLETED` chưa.
* Nếu đã hoàn thành, Service không quét lại từ đầu (lãng phí tài nguyên và làm phiền server đích), mà đọc kết quả từ bảng `scans` + `findings` và **phát lại ngay sự kiện `complete`** về cho client!
* ⚠️ Replay **chỉ** áp dụng cho trạng thái `COMPLETED`. Nếu client kết nối lại khi scan còn `RUNNING`, `stream_scan` sẽ chạy lượt quét mới (xem lưu ý ở 2.3) — đó là lý do trình duyệt phía frontend không được để `EventSource` tự reconnect.

## 🔑 4. Key Takeaways

1. **Service Layer** là chuẩn mực giúp code backend tách bạch rõ ràng giữa xử lý giao thức (HTTP) và logic nghiệp vụ.
2. Luôn chú ý **vòng đời của DB Session** giữa HTTP request thread và Background async task.
3. Khi làm việc với tác vụ bất đồng bộ kéo dài, luôn phải thiết kế **khả năng hủy bỏ (Cancellation pattern)** và xử lý `asyncio.CancelledError` đúng cách.
4. Cơ chế **Replay** giúp ứng dụng có khả năng chịu lỗi cao (Fault-tolerant), client rớt mạng kết nối lại vẫn xem được đầy đủ báo cáo.
