# Task 4.1 — Backend Dockerfile (Multi-stage Build)

> **Mục tiêu:** Đóng gói backend thành một Docker image **nhỏ, chạy không cần quyền root, và không phải đoán xem lúc chạy có thiếu file gì không** — bằng kỹ thuật multi-stage build.

---

## 📚 Lý thuyết: Multi-stage build là gì, và vì sao cần

### Vấn đề của Dockerfile 1 stage

Một Dockerfile thông thường (1 `FROM`) gộp chung **mọi thứ dùng để build** và **mọi thứ cần để chạy** vào cùng một image:
```dockerfile
FROM python:3.12-slim
RUN apt-get install -y build-essential   # chỉ cần lúc CÀI, không cần lúc CHẠY
RUN pip install .                         # pip, cache tải gói, metadata build...
CMD ["uvicorn", "app.main:app", ...]
```
Mọi gói `apt-get` cài để *biên dịch* dependency (compiler, dev headers), cache của `pip`, và các file tạm trong lúc build **đều ở lại trong image cuối cùng** — vì Docker image là một chồng layer, xoá file ở layer sau không giải phóng dung lượng layer trước đã lưu nó.

### Giải pháp: build 1 nơi, chạy 1 nơi khác

Multi-stage build dùng **nhiều `FROM`** trong cùng 1 Dockerfile — mỗi `FROM` là một "stage" riêng biệt, có filesystem riêng. Stage sau có thể **copy có chọn lọc** vài file từ stage trước bằng `COPY --from=<tên stage>`, bỏ lại toàn bộ phần còn lại:

```dockerfile
FROM python:3.12-slim AS builder
# ... cài đặt, build — image này sẽ bị VỨT ĐI, không public ra ngoài

FROM python:3.12-slim AS runtime
COPY --from=builder /opt/venv /opt/venv   # chỉ lấy đúng kết quả cần
CMD [...]
```
Image cuối cùng (`runtime`) không hề biết `builder` từng cài những gì ngoài đúng những file được `COPY --from` chỉ định. Đây là lý do image cuối nhỏ hơn hẳn dù quá trình build có thể đã tải/cài rất nhiều thứ tạm thời.

### Venv làm "ranh giới" giữa 2 stage

Thay vì cài package thẳng vào Python hệ thống của stage build rồi cố gắng "lọc" ra cái gì cần copy, dự án dựng một **virtualenv** (`/opt/venv`) làm một thư mục độc lập gói gọn mọi thứ Python cần (interpreter riêng biệt về `site-packages`, không phải về binary) — copy nguyên `/opt/venv` sang stage sau là copy đúng, đủ, không thiếu:
```dockerfile
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"   # mọi `pip`/`python`/`uvicorn` sau dòng này dùng venv, không dùng hệ thống
RUN pip install -e .
```
```dockerfile
# Stage sau — PATH cũng phải trỏ lại venv, vì đây là process/image khác
ENV PATH="/opt/venv/bin:$PATH"
COPY --from=builder /opt/venv /opt/venv
```

## 📚 Lý thuyết: Thứ tự COPY quyết định tốc độ rebuild (layer caching) — và một giả định sai bị `docker build` bắt lỗi ngay lập tức

Docker cache từng layer theo thứ tự lệnh trong Dockerfile — nếu input của một lệnh không đổi (nội dung file được COPY, hoặc lệnh RUN y hệt), Docker **dùng lại kết quả cũ** thay vì chạy lại. Nhưng cache bị **vô hiệu từ layer đổi trở đi, kể cả các layer sau nó không đổi gì**. Vì vậy mẹo kinh điển là: COPY file **ít đổi nhất** trước, để bước tốn thời gian nhất (`pip install`, tải + cài toàn bộ dependency) được cache lại, không phải chạy lại mỗi lần chỉ sửa 1 dòng code.

**Giả định ban đầu (sai) khi viết file này:** vì dùng **editable install** (`pip install -e .`) — cơ chế chỉ đăng ký một "đường tắt" trỏ về thư mục dự án thay vì copy file — tưởng rằng có thể viết:
```dockerfile
COPY pyproject.toml ./
RUN pip install -e .      # (!) tưởng là chưa cần app/ tồn tại
COPY app/ ./app/
```
để giữ được lợi ích cache (chỉ cài lại dependency khi `pyproject.toml` đổi, không phải mỗi lần sửa code).

**Thực tế khi chạy `docker build`:**
```
error: package directory 'app' does not exist
Getting requirements to build editable: finished with status 'error'
```
Dù là editable hay không, `setuptools` vẫn phải **đọc `app/` ngay lúc cài** để sinh metadata (`egg-info`) — vì `pyproject.toml` khai báo `[tool.setuptools] packages = ["app"]`, chỉ đích danh thư mục đó. Editable install chỉ tiết kiệm việc **copy file vào site-packages**, không tiết kiệm được việc **đọc file để biết nó tồn tại và lấy thông tin gói**.

**Sửa:** chấp nhận đánh đổi — `COPY app/` (và `templates/`, `alembic.ini`, vì chúng không ảnh hưởng gì tới việc cache) **trước** `RUN pip install`:
```dockerfile
COPY pyproject.toml ./
COPY app/ ./app/
COPY alembic.ini ./
COPY templates/ ./templates/
RUN pip install --no-compile -e .
```
Giờ mỗi lần sửa code, bước `pip install` sẽ chạy lại (không tận dụng được cache), nhưng đổi lại **build thành công** — đây là ví dụ cụ thể cho nguyên tắc "đúng trước, nhanh sau": một layer cache tối ưu mà không build được thì vô nghĩa. Với dependency list ổn định và không có bước compile nặng, cái giá của việc chạy lại `pip install` mỗi lần cũng không quá lớn.

> 🔑 **Bài học lớn nhất của cả Task 4.1:** giả định "chắc là đúng" về cách một công cụ hoạt động (ở đây: tưởng editable install trì hoãn việc đọc source) **luôn cần được xác minh bằng cách chạy thật**, không chỉ suy luận lý thuyết. `docker build` bắt lỗi này trong vài giây đầu tiên — sẽ tốn công hơn nhiều nếu để tới lúc build CI hoặc deploy mới phát hiện ra.

## 📚 Lý thuyết: Vì sao container không nên chạy bằng root

Mặc định, một container Docker chạy process bên trong với quyền **root** (UID 0) trừ khi Dockerfile nói khác. Vấn đề: nếu ứng dụng có lỗ hổng (RCE qua một dependency, hay chính logic ứng dụng), kẻ tấn công chiếm được process đó sẽ có **toàn quyền root bên trong container** — dù container có cơ chế cách ly với host, root-trong-container vẫn nguy hiểm hơn hẳn user thường (dễ khai thác thêm các lỗ hổng "thoát container"/container breakout, có toàn quyền ghi mọi file trong container, dễ cài thêm công cụ tấn công).

**Nguyên tắc defence in depth (phòng thủ nhiều lớp):** không vì đã có lớp cách ly container mà bỏ qua lớp phân quyền bên trong nó. Tạo user riêng:
```dockerfile
RUN groupadd --system --gid 1000 webguard \
    && useradd --system --uid 1000 --gid webguard --home-dir /app --shell /usr/sbin/nologin webguard
...
RUN chown -R webguard:webguard /app
USER webguard
```
- `--system`: tạo system account (không có mật khẩu, không dùng để đăng nhập tương tác) — đúng bản chất của user chỉ-để-chạy-service.
- `--shell /usr/sbin/nologin`: dù ai đó `docker exec` vào container và thử `su webguard`, không mở được shell tương tác.
- `chown` **phải chạy trước** `USER webguard` — sau dòng `USER`, mọi lệnh kế tiếp (gồm cả `RUN` còn lại) chạy với quyền user đó, không còn quyền `chown` tài sản thuộc root nữa.

## 📚 Bug tìm được khi rà soát: thiếu `templates/`, dùng sai mục đích `curl`

### 1. `ReportService` sẽ lỗi khi xuất báo cáo HTML trong Docker (chưa ai phát hiện vì chưa test)

Dockerfile gốc chỉ có `COPY app/ ./app/` — **không copy `templates/`**. Nhưng `ReportService` (xem `2.10`) tải template bằng đường dẫn tương đối tính từ vị trí file Python:
```python
TEMPLATES_DIR = Path(__file__).resolve().parent.parent.parent / "templates"
```
Thiếu `templates/` trong image nghĩa là `GET /report/{id}/export?format=html` sẽ ném `TemplateNotFound` — **một tính năng đã có từ Sprint 2 nhưng chưa từng chạy đúng trong Docker**, vì chưa ai thử export HTML từ container trước đây. Đã thêm `COPY app/templates ./templates` (qua stage builder rồi copy tiếp sang runtime).

> 🔑 **Bài học:** Dockerfile khai báo tường minh TỪNG thứ ứng dụng cần — không có gì "tự nhiên có mặt" như khi chạy trực tiếp từ thư mục dự án đầy đủ. Thiếu một file không dùng tới trong luồng test thông thường (ở đây: export HTML) có thể "ẩn" rất lâu cho tới khi ai đó dùng đúng tính năng đó trên đúng môi trường đó.

### 2. `curl` chỉ để healthcheck — đổi sang `urllib` có sẵn để bớt 1 package

Dockerfile gốc cài `curl` (qua `apt-get`) chỉ để `docker-compose.yml` gọi `curl -f http://localhost:8000/...` làm healthcheck. Nhưng Python đã có `urllib.request` **built-in** — không cần thêm package nào:
```dockerfile
HEALTHCHECK ... CMD python -c "import sys,urllib.request as u; sys.exit(0 if u.urlopen('http://localhost:8000/api/v1/health', timeout=3).status == 200 else 1)"
```
Kết quả: stage runtime **không cần `apt-get install` gì cả** — base `python:3.12-slim` vốn đã có sẵn `ca-certificates` (cần cho mọi request HTTPS của chính scanner, không liên quan gì tới curl) vì chính `pip` cũng cần nó để tải package qua HTTPS lúc build.

## 📚 Bug liên quan tìm được: volume khai báo nhưng không ai ghi vào đó

`docker-compose.yml` (bản cũ) có:
```yaml
environment:
  - WEBGUARD_DB_URL=sqlite:///./webguard.db   # ghi vào /app/webguard.db
volumes:
  - backend_data:/app/data                     # nhưng volume lại gắn ở /app/data
```
SQLite URL `sqlite:///./webguard.db` (3 dấu `/`, path tương đối) tạo file ở `/app/webguard.db` — **không nằm trong** thư mục `/app/data` mà volume `backend_data` quản lý. Hệ quả: dữ liệu quét **mất sạch** mỗi khi container bị xoá và tạo lại (`docker compose down && up`, hay khi redeploy) — volume tồn tại nhưng không bảo vệ được gì, vì không ai ghi vào đúng chỗ nó theo dõi.

Đã sửa: `WEBGUARD_DB_URL=sqlite:////app/data/webguard.db` (4 dấu `/` = path **tuyệt đối** `/app/data/webguard.db`, đúng bên trong volume). Áp dụng cho cả `docker-compose.yml` (production) và `docker-compose.dev.yml`.

> 💡 **Cú pháp SQLite URL dễ nhầm:** `sqlite:///path` (3 slash) = path **tương đối** với thư mục làm việc hiện tại; `sqlite:////path` (4 slash) = path **tuyệt đối** (`/path`). Rất dễ gõ thiếu/thừa 1 dấu `/` mà không có lỗi gì ngay lập tức — SQLite vẫn tạo file bình thường, chỉ là tạo **sai chỗ**.

## 💻 Kết quả: Dockerfile hoàn chỉnh

File: `backend/Dockerfile` (xem file thật — đã thêm comment giải thích từng quyết định ngay trong file).

```dockerfile
FROM python:3.12-slim AS builder
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /app
COPY pyproject.toml ./
COPY app/ ./app/
COPY alembic.ini ./
COPY templates/ ./templates/
RUN pip install --no-compile -e .

FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PATH="/opt/venv/bin:$PATH"
RUN groupadd --system --gid 1000 webguard \
    && useradd --system --uid 1000 --gid webguard --home-dir /app --shell /usr/sbin/nologin webguard
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY --from=builder /app/app ./app
COPY --from=builder /app/alembic.ini ./
COPY --from=builder /app/templates ./templates
RUN mkdir -p /app/data && chown -R webguard:webguard /app
USER webguard
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
    CMD python -c "import sys,urllib.request as u; sys.exit(0 if u.urlopen('http://localhost:8000/api/v1/health', timeout=3).status == 200 else 1)"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### Vì sao không cần `alembic.ini` để app chạy, nhưng vẫn copy nó

`app/db/session.py.init_db()` tự tạo schema bằng `Base.metadata.create_all()` (xem `2.7`, `2.8`) — **không** gọi Alembic lúc runtime. Vậy image hoàn toàn chạy được mà không cần `alembic.ini`. Nhưng vẫn copy vào vì: ai đó muốn `docker exec` vào container rồi chạy `alembic upgrade head` thủ công (áp dụng migration có kiểm soát thay vì để `create_all` tự lo) cần file này — chi phí gần như bằng 0 (vài KB) cho một khả năng hữu ích.

### `.dockerignore` — lợi ích dù Dockerfile đã COPY có chọn lọc

Dockerfile này chỉ `COPY` đích danh từng thứ cần (`app/`, `alembic.ini`, `templates/`, `pyproject.toml`) nên về mặt **nội dung image**, `.dockerignore` không thay đổi gì. Nhưng nó vẫn có 2 lợi ích thật:
1. **Build context nhỏ hơn, build nhanh hơn:** mọi lần `docker build`, Docker CLI **gửi toàn bộ thư mục** (trừ phần bị ignore) cho daemon trước khi build — một thư mục có sẵn `.venv/`, `htmlcov/`, `webguard.db` từ lúc dev local sẽ bị gửi theo dù không dòng COPY nào đụng tới chúng.
2. **Lưới an toàn cho tương lai:** nếu sau này ai đó đổi Dockerfile sang `COPY . .` (dễ gặp khi dự án lớn dần), `.dockerignore` là thứ duy nhất ngăn `webguard.db` (có thể chứa dữ liệu quét thật) hay `.env` lọt vào image.

## 🔑 Takeaway

1. **Multi-stage build = build một nơi, chạy một nơi khác** — stage cuối chỉ chứa đúng những gì được `COPY --from` chỉ định, không "thừa kế" bất kỳ thứ gì khác từ các stage trước.
2. **Virtualenv là đơn vị copy gọn gàng giữa các stage** — tự chứa toàn bộ dependency đã cài, không phụ thuộc Python hệ thống của stage đích.
3. **Thứ tự COPY quyết định cache** — đặt file ít đổi nhất trước bước tốn thời gian nhất; nhưng cái giá phải trả (ở đây: bắt buộc dùng editable install) cần được hiểu rõ, không chỉ copy công thức.
4. **Non-root user là một lớp phòng thủ độc lập**, không thay thế cho việc vá lỗ hổng ứng dụng, nhưng làm giảm thiệt hại nếu có lỗ hổng chưa biết.
5. **Viết Dockerfile là lúc lộ ra những giả định ngầm của code** (ví dụ `templates/` phải là sibling của `app/`) — những giả định này vô hình khi chạy trực tiếp từ thư mục dự án đầy đủ, chỉ hiện ra khi đóng gói có chọn lọc.
6. **Một volume không tự động "làm việc"** — nó chỉ bảo vệ đúng thư mục nó được mount vào; ứng dụng phải thực sự ghi dữ liệu vào đúng thư mục đó.
