## 🧭 1. Tại sao cần tách riêng bước "Khởi tạo Scan"?

Trong các ứng dụng thông thường, khi bạn bấm "Submit", server xử lý ngay trong 0.1 giây rồi trả kết quả. Nhưng với một **Security Scanner**:
- Quét đủ `full` (7 module: Headers, Cookies, SSL/TLS, Info Leak, CORS, Content, HTTP Config) mất từ **5 đến 30 giây** — lâu hơn con số ban đầu (5 module) vì `InformationModule` và `HttpConfigModule` tự thêm nhiều request dò (xem `1.5`, `1.12`).
- Nếu giữ kết nối HTTP để chờ quét xong mới trả về:
  - Trình duyệt sẽ quay vòng tròn đơ cứng, dễ bị lỗi quá thời gian (HTTP Request Timeout).
  - Người dùng không biết công cụ đang quét đến đâu hay đã bị treo.

### Giải pháp chuyên nghiệp: Kiến trúc Bất đồng bộ (Async Lifecycle)
Thay vì bắt khách hàng đứng đợi:
1. **Bước 1 (Task 2.2 này):** Client gửi URL lên -> Server kiểm tra hợp lệ -> Cấp ngay một mã vé lượt quét `scan_id` với trạng thái `pending` (chờ quét) và trả lời ngay lập tức trong vài mili-giây.
2. **Bước 2 (Task 2.3 tiếp theo):** Client cầm `scan_id` này mở một đường truyền thời gian thực (SSE Stream) để theo dõi tiến trình chạy từng module.

```
Client ──[ POST /api/v1/scan (kèm target URL) ]──> FastAPI
Client <──[ Trả về ngay: scan_id = "abc-123", status = "pending" ]─── FastAPI (Xong trong 15ms)
   │
   └──(Cầm scan_id kết nối tiếp sang SSE ở Task 2.3 để xem kết quả trực tiếp)
```

## 🛡️ 2. Kiến thức An ninh mạng Cốt lõi: Lỗ hổng SSRF là gì?

> ⚠️ **Điểm phỏng vấn quan trọng:** Các công cụ quét bảo mật (Security Scanners) chính là đối tượng số một mà tin tặc nhắm đến để khai thác SSRF!

### Khái niệm SSRF (Server-Side Request Forgery)
SSRF là lỗ hổng xảy ra khi một ứng dụng web nhận một URL từ người dùng và máy chủ tự động gửi request đến URL đó mà **không kiểm tra điểm đến**.

### Kịch bản kẻ tấn công lợi dụng Scanner:
Hệ thống WebGuard của bạn được đặt trong một mạng nội bộ doanh nghiệp.
1. Tin tặc không thể tự mình truy cập vào cơ sở dữ liệu nội bộ `http://192.168.1.50:5432` hoặc trang quản trị nội bộ `http://localhost:8080/admin`.
2. Tin tặc vào WebGuard và nhập URL cần quét là: `http://192.168.1.50` hoặc `http://127.0.0.1:8000`.
3. Lúc này, **chính server WebGuard** đứng ra gửi request thay cho tin tặc!
4. Máy chủ WebGuard vô tình trở thành "tay trong" (proxy trung gian) giúp tin tặc dò quét và đánh cắp tài liệu mật trong toàn bộ mạng nội bộ công ty.

```
[Tin tặc bên ngoài] ──(Nhập target: http://192.168.1.50)──> [Server WebGuard]
                                                                   │
                                                        (WebGuard gửi request tới)
                                                                   ▼
                                                     [Database Mật Nội Bộ: 192.168.1.50]
                                                     (Lộ dữ liệu nhạy cảm cho hacker!)
```

## 🔒 3. Cơ chế phòng thủ SSRF 4 lớp trong WebGuard

Có **hai nơi** kiểm tra: (a) validator của Pydantic trong [`backend/app/schemas/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/schemas/scan.py) kiểm tra *cú pháp và IP viết thẳng trong URL*, trả `422`; (b) hàm `assert_public_target` trong [`backend/app/core/security.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/core/security.py) **phân giải DNS** rồi kiểm tra địa chỉ thật, trả `400`.

### (a) Validator Pydantic — lớp 1, 2, 3

```python
@field_validator("url")
@classmethod
def validate_target_url(cls, v: str) -> str:
    url_str = v.strip()
    parsed = urlparse(url_str)

    # 🛑 LỚP 1: Bắt buộc giao thức an toàn
    if parsed.scheme not in ("http", "https"):
        raise ValueError("URL phải bắt đầu bằng giao thức http:// hoặc https://")

    hostname = parsed.hostname
    if not hostname:
        raise ValueError("URL không hợp lệ, không tìm thấy hostname")

    # 🛑 LỚP 2: Chặn tên miền / địa chỉ loopback cục bộ
    if hostname.lower() in ("localhost", "127.0.0.1", "0.0.0.0"):
        raise ValueError("Không được phép quét localhost hoặc địa chỉ loopback cục bộ")

    # 🛑 LỚP 3: Chặn IP không công khai (viết thẳng trong URL)
    try:
        ip = ipaddress.ip_address(hostname)
        is_ip = True
    except ValueError:
        is_ip = False          # là tên miền chữ (vd example.com), không phải IP
    if is_ip and not ip.is_global:
        raise ValueError("Không được phép quét dải địa chỉ IP mạng nội bộ (Private IP)")

    return url_str
```

> 🐞 **Cạm bẫy kinh điển — đừng viết `raise` bên trong `try ... except ValueError`:**
> ```python
> try:
>     ip = ipaddress.ip_address(hostname)
>     if ip.is_private: raise ValueError("chặn!")   # ← bị chính khối except bên dưới nuốt mất
> except ValueError:
>     pass
> ```
> `ipaddress.ip_address()` ném `ValueError` khi `hostname` không phải IP, nên ta bắt `ValueError` để bỏ qua tên miền chữ. Nhưng nếu *cũng* `raise ValueError` trong cùng khối `try`, lỗi "chặn!" bị bắt luôn → **IP nội bộ lọt qua**. Cách đúng (như code thật): chỉ bọc đúng dòng gọi `ip_address()` trong `try`, ghi lại kết quả vào cờ `is_ip`, rồi kiểm tra điều kiện **ở ngoài** khối `try`.

`ip.is_global` (thay vì chỉ `is_private`) chặn rộng hơn: private (RFC 1918), loopback, link-local (`169.254.0.0/16` — gồm cloud metadata), CGNAT (`100.64.0.0/10`), reserved (`240.0.0.0/4`), unspecified (`0.0.0.0`) và IPv6 tương ứng (`::1`, `fe80::/10`, `fc00::/7`…). Lưu ý `is_global` vẫn trả `True` cho địa chỉ **multicast** (`224.0.0.0/4`) — vô hại vì không thể mở kết nối TCP tới multicast.

### (b) Phân giải DNS — lớp 4

Validator ở trên **không** thấy được kiểu tấn công *tên miền trỏ về IP nội bộ*: `http://169-254-169-254.attacker.com` hay `http://localtest.me` (trỏ về `127.0.0.1`) trông như tên miền bình thường.

```python
async def assert_public_target(url: str) -> None:
    hostname = urlparse(url).hostname
    try:
        addresses = await _resolve(hostname)      # loop.getaddrinfo — không chặn event loop
    except socket.gaierror:
        return                                    # không phân giải được → để scan tự báo lỗi
    for address in addresses:
        if not ipaddress.ip_address(address).is_global:
            raise InvalidTargetException("Tên miền phân giải về địa chỉ mạng nội bộ ...")
```

- Kiểm tra **mọi** địa chỉ trả về (một tên miền có thể có nhiều bản ghi A/AAAA); chỉ cần một địa chỉ nội bộ là chặn.
- Gọi trong route `POST /scan` (hàm `async`), dùng `loop.getaddrinfo` để DNS không làm đứng server.
- **Giới hạn còn lại — DNS rebinding:** tên miền có thể trả IP public lúc ta kiểm tra, rồi trả IP nội bộ lúc `httpx` kết nối thật vài giây sau (TTL cực thấp). Chống triệt để cần *ghim IP đã phân giải* khi kết nối. Ngoài ra module không theo redirect (`follow_redirects` mặc định tắt) nên không bị lái sang địa chỉ nội bộ qua `Location`.

### Ý nghĩa của từng lớp bảo vệ:
1. **Lớp 1 — Scheme Whitelist (`http`/`https`):**
   - Chặn tin tặc dùng các scheme lạ như `file:///etc/passwd` (để đọc file hệ thống Linux) hoặc `gopher://`, `ftp://`.
2. **Lớp 2 — Chặn Loopback:**
   - Chặn ngay các từ khóa cơ bản: `localhost`, `127.0.0.1`, `0.0.0.0`.
3. **Lớp 3 — Chặn IP không công khai (RFC 1918 và hơn thế):**
   - Sử dụng thư viện chuẩn `ipaddress` của Python (`is_global`).
   - Tự động nhận diện và chặn mọi dải mạng nội bộ:
     - `10.0.0.0/8` (Mạng doanh nghiệp lớn)
     - `172.16.0.0/12` (Mạng Docker / Cloud nội bộ)
     - `192.168.0.0/16` (Mạng gia đình / Router nội bộ)
     - `169.254.0.0/16` (Link-local / AWS Metadata service - nơi lưu trữ AWS Keys)

## 📚 4. Khái niệm Kỹ thuật Bổ trợ

### Tại sao dùng UUID4 thay vì ID số tự tăng (1, 2, 3...)?
- **ID tự tăng (`id = 1, 2, 3`):** Kẻ xấu có thể đoán được các số tiếp theo hoặc số trước đó. Nếu họ sửa URL thành `/scan/1`, `/scan/2` thì họ có thể xem trộm toàn bộ báo cáo quét của người khác (đây gọi là lỗ hổng **IDOR - Insecure Direct Object Reference**).
- **UUID4 (`e7b4a2c1-8d19-4f76-b328-94719e09d123`):** Một chuỗi 128-bit ngẫu nhiên sinh ra từ thuật toán mật mã học. Không một ai có thể đoán trước được ID tiếp theo, đảm bảo tính riêng tư cho từng lượt quét.

> ⚠️ **UUID không thay thế việc xác thực.** UUID4 khiến ID *khó đoán*, nhưng ai có được ID (lộ qua log, lịch sử trình duyệt, chia sẻ link) vẫn xem được kết quả. WebGuard hiện **chưa có đăng nhập/phân quyền**; đây là công cụ cục bộ/demo. Nếu triển khai nhiều người dùng, phải thêm xác thực và gắn mỗi scan với chủ sở hữu.

### Trạng thái lượt quét (Scan Status Lifecycle)
Chúng ta định nghĩa trạng thái bằng Enum:
- `PENDING`: Mới được khởi tạo, đang chuẩn bị tài nguyên.
- `RUNNING`: Đang chạy các module quét.
- `COMPLETED`: Đã quét xong và tổng kết điểm.
- `FAILED`: Gặp sự cố không thể kết nối tới mục tiêu.
- `CANCELLED`: Người dùng chủ động hủy (xem 2.9).

## 💻 5. Code Endpoint Khởi tạo Scan

File: [`backend/app/api/v1/scan.py`](file:///d:/HuyMai/SelfLearning/Project/WebGuard/backend/app/api/v1/scan.py)

```python
@router.post("", response_model=ScanCreateResponse, status_code=status.HTTP_201_CREATED)
async def create_scan(payload: ScanCreateRequest, db: Session = Depends(get_db)) -> ScanCreateResponse:
    # 1. Lớp 4 chống SSRF: phân giải DNS, từ chối nếu trỏ về địa chỉ không công khai
    await assert_public_target(payload.url)

    # 2. ScanService sinh UUID, lưu bản ghi `pending` (kèm mode) vào SQLite
    scan = scan_service.create_scan(db=db, target_url=payload.url, mode=payload.mode.value)

    # 3. (Tương thích ngược) đồng bộ bộ nhớ đệm in-memory `scan_jobs`
    scan_jobs[scan.id] = {"scan_id": scan.id, "target_url": scan.target_url, "mode": scan.mode,
                          "status": ScanStatus(scan.status), "created_at": scan.created_at, "findings": []}

    # 4. Trả về thông tin cho Client kèm mã HTTP 201 (Created)
    return ScanCreateResponse(scan_id=scan.id, target_url=scan.target_url,
                              mode=ScanMode(scan.mode), status=ScanStatus(scan.status),
                              created_at=scan.created_at)
```

> 📌 Ở thời điểm viết task 2.2, endpoint chỉ lưu vào dict `scan_jobs` trong RAM; từ Task 2.7–2.9 dữ liệu được lưu vào **SQLite qua `ScanService`**, còn `scan_jobs` giữ lại như bộ nhớ đệm/phương án dự phòng. Đoạn code trên là phiên bản hiện tại.

## 🔑 Tóm tắt cốt lõi (Takeaway)

1. **Async Pattern:** Tách riêng khâu tạo lượt quét (`POST /scan`) để phản hồi tức thì (`201 Created`), không làm đơ giao diện người dùng.
2. **SSRF Defense:** Bắt buộc phải bảo vệ Scanner khỏi bị lợi dụng để dọ thám mạng nội bộ: chặn `localhost`, IP không công khai, giao thức không phải `http/https` **và tên miền phân giải về địa chỉ nội bộ** (kiểm tra cả IP viết trực tiếp lẫn kết quả DNS).
3. **Pydantic Validation:** Kiểm tra và chặn dữ liệu xấu ngay từ cửa ngõ API.
4. **UUID4:** Ngăn chặn lỗ hổng IDOR, bảo vệ dữ liệu lượt quét của người dùng.
