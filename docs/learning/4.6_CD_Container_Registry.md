# Task 4.6 — CD: Container Registry (build & push image lên GHCR)

> **Mục tiêu:** Khi code vào `main` hoặc khi gắn tag phiên bản `vX.Y.Z`, GitHub Actions tự build image backend + frontend và đẩy lên **GitHub Container Registry (GHCR)**. Ai cũng có thể `docker pull` về chạy mà không cần clone repo hay build.
>
> File triển khai: `.github/workflows/cd-publish-images.yml`

---

## 📚 Lý thuyết

### CI vs CD
- **CI** (4.4, 4.5): kiểm tra code có đúng không.
- **CD** (Delivery): biến code đã đúng thành **artifact có thể triển khai** — ở đây là Docker image có tên, có phiên bản, nằm trên registry.

### Container registry & GHCR
Registry là "kho chứa image" (giống npm cho package). GHCR (`ghcr.io`) gắn liền với GitHub: không cần tài khoản Docker Hub riêng, xác thực bằng chính `GITHUB_TOKEN` của workflow, quyền truy cập theo repo.

Tên image: `ghcr.io/<owner>/<repo>-backend:<tag>`. **GHCR bắt buộc chữ thường** — repo `WebGuard` có chữ hoa, nên phải lowercase (xem bên dưới).

### Tag image: đừng chỉ dùng `latest`
| Tag | Từ đâu | Dùng để |
|---|---|---|
| `main` | push vào main | bản mới nhất đang phát triển |
| `sha-abc1234` | commit | **bất biến**, truy ngược chính xác commit nào |
| `1.2.3`, `1.2` | git tag `v1.2.3` | phát hành chính thức; `1.2` tự trôi theo bản vá |
| `latest` | chỉ khi có tag `v*` | bản phát hành ổn định mới nhất |

> `latest` **chỉ gán khi có tag phát hành**, không gán cho mỗi lần push main — nếu không, "latest" thực chất là "bản main chưa chắc ổn định", dễ gây nhầm.

## 🛠 Thiết kế workflow & lý do

### 1. Không chạy trên `pull_request`
```yaml
on:
  push:
    branches: [main]
    tags: ["v*.*.*"]
  workflow_dispatch:
```
PR (nhất là từ fork) **không được phép publish** gì cả. Cổng chặn PR là CI. `workflow_dispatch` cho phép bấm chạy tay khi cần.

### 2. Quyền tối thiểu
```yaml
permissions:
  contents: read
  packages: write
```
`GITHUB_TOKEN` chỉ được đọc code và ghi package — không hơn. Không cần tạo Personal Access Token, nên không có secret dài hạn nào để lộ.

### 3. Matrix cho 2 image
Một job định nghĩa, chạy 2 lần (backend, frontend) song song; `fail-fast: false` để một bên lỗi không huỷ bên kia.

### 4. Frontend phải có `target: production`
Dockerfile frontend có nhiều stage, stage **cuối** là `dev` (Vite dev server). Nếu không chỉ `target`, Docker build stage cuối → publish nhầm image dev. Đây chính là bug đã gặp ở 4.2 và 4.3, nên ở đây ghi tường minh. Backend để `target` rỗng (stage cuối `runtime` là cái cần).

### 5. `docker/metadata-action` sinh tag + nhãn
- Tự **lowercase** tên image (giải quyết vụ chữ hoa của GHCR).
- Tự thêm nhãn OCI (`org.opencontainers.image.source`, `revision`...) → GHCR tự **liên kết package với repo**.

### 6. Cache build bằng GitHub Actions cache
`cache-from/to: type=gha,scope=<name>`. `scope` tách riêng cache backend và frontend để không ghi đè nhau. `mode=max` lưu cả layer của stage trung gian (builder/build) — chính là phần tốn thời gian (cài dependency).

### 7. `concurrency` với `cancel-in-progress: false`
Khác với CI: ở CI huỷ lần chạy cũ là hợp lý. Ở CD, huỷ giữa chừng có thể để lại tag đẩy dở, nên để chạy xong rồi mới đến lượt kế.

## ✅ Kiểm chứng

Chưa chạy được thật vì cần GitHub. Các bước kiểm tra sau khi push:
1. Merge vào `main` → tab **Actions** thấy 2 job `Publish backend`, `Publish frontend`.
2. Repo → **Packages**: xuất hiện `webguard-backend`, `webguard-frontend` với tag `main`, `sha-...`.
3. Thử phát hành: `git tag v0.1.0 && git push origin v0.1.0` → thêm tag `0.1.0`, `0.1`, `latest`.
4. Kéo thử: `docker pull ghcr.io/<owner>/webguard-frontend:main`.

> ⚠️ **Lưu ý khi dùng thật:** package mới tạo mặc định **private**. Muốn người khác pull không cần đăng nhập, phải vào Package settings → đổi sang **Public** (làm 1 lần bằng tay trên GitHub UI, workflow không tự đổi được).

---

## 🔑 Bài học
1. **CD tách khỏi CI**: CI chặn PR, CD chỉ chạy trên nhánh/tag đã tin cậy.
2. **Tag có ý nghĩa**: `sha-` để truy vết, semver để phát hành, `latest` chỉ cho bản phát hành.
3. **Quyền tối thiểu + `GITHUB_TOKEN`** thay vì PAT.
4. **Luôn chỉ rõ `target`** khi Dockerfile nhiều stage.
