# Task 4.10 — `CONTRIBUTING.md`

> **Mục tiêu:** Một file ở gốc repo giúp người mới đi từ "vừa clone" đến "PR được merge" mà không phải hỏi ai.
>
> File triển khai: `CONTRIBUTING.md` (viết bằng tiếng Anh, cùng ngôn ngữ với `README.md` và `SECURITY.md`; các tài liệu chi tiết trong `docs/` giữ tiếng Việt và được liên kết sang)

---

## 📚 Lý thuyết

### Vì sao tên file và vị trí quan trọng
GitHub **nhận diện đặc biệt** `CONTRIBUTING.md` ở gốc repo (hoặc `.github/`, `docs/`): khi ai đó mở Issue hoặc PR mới, GitHub hiện link tới file này. Đặt đúng chỗ = người đóng góp *thấy* nó đúng lúc cần.

### Một CONTRIBUTING tốt trả lời theo thứ tự người đọc hỏi
1. Làm sao chạy được? → *một lệnh* (task 4.8)
2. Code nằm đâu? → bảng cấu trúc thư mục
3. Quy trình thế nào? → nhánh, commit, PR
4. Làm sao biết PR tôi ổn? → bảng lệnh khớp với CI
5. Việc hay gặp làm thế nào? → thêm check/module, đổi schema
6. Báo lỗi / lỗ hổng ở đâu? → issue vs `SECURITY.md`

### Tránh trùng lặp, trỏ tới nguồn gốc
File **không chép lại** `GIT_CONVENTIONS.md`, `SETUP_GUIDE.md`, `ARCHITECTURE.md` — chỉ tóm tắt và liên kết. Hai bản sao của cùng một quy tắc sớm muộn sẽ lệch nhau.

## 🛠 Các quyết định

### Bảng "Checks your PR must pass" khớp từng lệnh với workflow CI
Gom các task 4.4 → 4.7 thành một chỗ: người đóng góp chạy đúng lệnh CI chạy trước khi push, nên hiếm khi gặp build đỏ. Mỗi dòng ghi rõ workflow nào chạy nó. Dòng `npm test` ghi "— (run locally)" vì CI frontend **chưa** chạy vitest (xem ghi chú ở `4.5`), tránh hứa điều chưa đúng.

### Mục "Scope & safety rules for scanners"
Đặc thù của dự án: một công cụ quét bảo mật dễ bị đóng góp theo hướng nguy hiểm (thêm payload tấn công, brute-force). Quy tắc "chỉ *đọc* những gì mục tiêu đã công khai, không khai thác" được nêu thành luật cho người đóng góp, khớp với phần *Scope & Safety* trong README. Kèm nguyên tắc "check báo sai (false positive) còn tệ hơn không có check" — phản ánh bài học từ các lần sửa false positive ở các module trước.

### Hướng dẫn thêm module dựa trên code thật
Mô tả `BaseModule` (`name`, `description`, `async scan(url)`), `Finding` ở `app/schemas/scan.py`, và nơi đăng ký ở `modules/scanner.py` — đã đối chiếu với code trước khi viết, không viết theo trí nhớ.

### Báo lỗ hổng: tách khỏi issue công khai
Chỉ rõ **không** mở public issue cho lỗ hổng bảo mật → chuyển sang `SECURITY.md`. Với một dự án bảo mật, đây là điểm cần thiết.

## ✅ Kiểm chứng
- Mọi đường dẫn liên kết (`docs/*.md`, `SECURITY.md`, `scripts/*`) đã đối chiếu tồn tại.
- Mọi lệnh trong bảng CI khớp với workflow tương ứng trong `.github/workflows/`.
- Tham chiếu mã (`BaseModule`, `Finding`, `scanner.py`, thư mục migrations) đã kiểm tra bằng cách đọc code.

## 🔑 Bài học
1. **Viết cho người chưa biết gì**, sắp xếp theo thứ tự câu hỏi họ sẽ có.
2. **Một nguồn sự thật:** liên kết thay vì sao chép.
3. **Tài liệu cũng cần "kiểm thử":** đối chiếu với code và CI thật, không dựa vào trí nhớ.
4. **Nêu rõ ranh giới của dự án** — đặc biệt khi dự án là công cụ bảo mật.
